What is PostgreSQL?

📖 10 min read 🎯 Foundation

PostgreSQL (pronounced post-gress-Q-L, often called Postgres) is a powerful, open-source relational database system with over 35 years of active development. It is trusted by companies like Apple, Instagram, Spotify, Reddit, and countless others.

Why PostgreSQL?

🆓

Free & Open Source

No licensing costs. Backed by a vibrant global community since 1986.

🔒

ACID Compliant

Rock-solid transactions — Atomicity, Consistency, Isolation, Durability guaranteed.

🧩

Extensible

Custom data types, functions, operators, and extensions like PostGIS, pgvector.

📊

SQL Standard

Most SQL-standard compliant RDBMS available. Your SQL skills transfer directly.

🌐

JSON & NoSQL

Full JSONB support means relational + document storage in one database.

⚡

High Performance

Parallel queries, advanced indexing (B-tree, GIN, GiST, BRIN), partitioning.

PostgreSQL vs SQL Server — At a Glance

🔄

If you know SQL Server, PostgreSQL will feel familiar. The SQL syntax is very similar. The key differences are in tooling (pgAdmin vs SSMS), object ownership (schemas work differently), and configuration (no GUI wizard — everything is SQL commands).

The PostgreSQL Architecture

Understanding the architecture helps you manage and troubleshoot your database. Here's the hierarchy:

1

PostgreSQL Server (Instance)

The running database server process. One server can host many databases.

2

Database

An isolated container. Each database has its own users, schemas, and tables. (e.g., myapp_db)

3

Schema

A namespace inside a database. The default schema is public. You can create schemas like sales, hr.

4

Table

Where data lives — rows and columns. Belongs to a schema. Full name: schema.table → public.orders

5

Row (Tuple)

A single record in a table. PostgreSQL calls rows "tuples" internally.

Creating Tables

The CREATE TABLE statement defines the structure of your data. Each column has a name and a data type.

Create customers table
CREATE TABLE customers (
    customer_id   SERIAL        PRIMARY KEY,
    first_name    VARCHAR(100)  NOT NULL,
    last_name     VARCHAR(100)  NOT NULL,
    email         VARCHAR(255)  UNIQUE NOT NULL,
    phone         VARCHAR(20),
    city          VARCHAR(100),
    created_at    TIMESTAMP     DEFAULT NOW()
);
Create products table
CREATE TABLE products (
    product_id    SERIAL          PRIMARY KEY,
    name          VARCHAR(200)    NOT NULL,
    category      VARCHAR(100),
    price         NUMERIC(10,2)   NOT NULL,
    stock_qty     INTEGER         DEFAULT 0,
    is_active     BOOLEAN         DEFAULT TRUE,
    created_at    TIMESTAMP       DEFAULT NOW()
);
Create orders table
CREATE TABLE orders (
    order_id      SERIAL          PRIMARY KEY,
    customer_id   INTEGER         NOT NULL REFERENCES customers(customer_id),
    order_date    TIMESTAMP       DEFAULT NOW(),
    total_amount  NUMERIC(12,2)   NOT NULL DEFAULT 0,
    status        VARCHAR(50)     DEFAULT 'pending',
    notes         TEXT
);

Modifying Tables (ALTER TABLE)

ALTER TABLE examples
-- Add a column
ALTER TABLE customers ADD COLUMN country VARCHAR(100);

-- Remove a column

-- Rename a column
ALTER TABLE customers RENAME COLUMN city TO city_name;

-- Change a column's data type
ALTER TABLE products ALTER COLUMN stock_qty TYPE BIGINT;

-- Rename a table

View table structure

\d customers

Quick Check: What does SERIAL do in PostgreSQL?

✅ Correct! SERIAL is shorthand for an integer column backed by a sequence — equivalent to IDENTITY(1,1) in SQL Server. Each new row gets the next number automatically.
❌ Not quite. SERIAL creates an auto-incrementing integer — like IDENTITY(1,1) in SQL Server. Each INSERT gets the next number automatically.

PostgreSQL Pro Tip: Use TEXT liberally

In PostgreSQL, TEXT and VARCHAR(n) have identical performance. Unlike SQL Server, there's no NVARCHAR needed — TEXT handles Unicode automatically. Use TEXT when you don't have a strong reason to limit length.

Type Casting

INSERT — Adding Data

📖 15 min🛠 Hands-on

The INSERT INTO statement adds new rows to a table. Let's populate our e-commerce tables.

Basic INSERT

Single row insert
-- Insert a single customer
INSERT INTO customers (first_name, last_name, email, city)
VALUES ('Priya', 'Sharma', 'priya@example.com', 'Hyderabad');

-- Note: customer_id and created_at are auto-generated (SERIAL + DEFAULT)

INSERT Multiple Rows

Bulk insert
INSERT INTO customers (first_name, last_name, email, city)
VALUES
    ('Rahul',   'Verma',   'rahul@example.com',   'Mumbai'),
    ('Anjali',  'Patel',   'anjali@example.com',  'Bangalore'),
    ('Suresh',  'Kumar',   'suresh@example.com',  'Chennai'),
    ('Deepika', 'Nair',    'deepika@example.com', 'Kochi');

-- PostgreSQL inserts all 4 rows in one statement

INSERT Products

Insert product data
INSERT INTO products (name, category, price, stock_qty)
VALUES
    ('Laptop Pro 15"',    'Electronics',  85000.00, 25),
    ('Wireless Mouse',    'Electronics',  1299.00,  150),
    ('Office Desk Chair', 'Furniture',     12500.00, 40),
    ('Coffee Maker',      'Appliances',    4500.00,  60),
    ('Notebook A4 Pack',  'Stationery',    250.00,   500);

INSERT with RETURNING

This is a powerful PostgreSQL feature with no SQL Server equivalent. You can get back the inserted row's data immediately — very useful for getting auto-generated IDs.

INSERT ... RETURNING
-- Get the new customer_id right after inserting
INSERT INTO customers (first_name, last_name, email)
VALUES ('Vikram', 'Singh', 'vikram@example.com')
RETURNING customer_id, created_at;

-- Returns:
-- customer_id |        created_at
-- ────────────+──────────────────────────
--           6 | 2025-06-18 10:30:00.123

UPSERT — INSERT or UPDATE (ON CONFLICT)

Upsert is the pattern "insert if not exists, update if it does." PostgreSQL's syntax is elegant.

ON CONFLICT (Upsert)
-- Insert, or update price/stock if product name already exists
INSERT INTO products (name, category, price, stock_qty)
VALUES ('Wireless Mouse', 'Electronics', 1199.00, 200)
ON CONFLICT (name)
DO UPDATE SET
    price     = EXCLUDED.price,
    stock_qty = EXCLUDED.stock_qty;

-- EXCLUDED refers to the row that WOULD have been inserted

-- Or: do nothing on conflict
INSERT INTO customers (email, first_name, last_name)
VALUES ('priya@example.com', 'Priya', 'S')
ON CONFLICT (email) DO NOTHING;
🔄

SQL Server MERGE vs PostgreSQL ON CONFLICT

SQL Server uses MERGE for upsert operations. PostgreSQL's INSERT ... ON CONFLICT is simpler and safer. PostgreSQL 15+ also has a MERGE statement if you prefer that syntax.

The SELECT statement is the most used SQL command. Mastering it means mastering PostgreSQL.

Basic SELECT

SELECT examples
-- Select all columns
SELECT * FROM customers;

-- Select specific columns

    first_name  AS "First Name",
    last_name   AS "Last Name",

Filtering with WHERE

WHERE clause
-- Exact match
SELECT * FROM customers WHERE city = 'Hyderabad';

-- Numeric comparisons
SELECT name, price FROM products WHERE price > 5000;
SELECT name, price FROM products WHERE price BETWEEN 1000 AND 10000;

-- Pattern matching (LIKE)
SELECT * FROM customers WHERE email LIKE '%@example.com';
SELECT * FROM products WHERE name ILIKE '%laptop%';  -- ILIKE = case-insensitive

-- Multiple conditions
SELECT * FROM products
WHERE category = 'Electronics'
  AND price < 2000
  AND is_active = TRUE;

-- IN list
SELECT * FROM customers
WHERE city IN ('Hyderabad', 'Mumbai', 'Bangalore');

-- NULL checks
SELECT * FROM customers WHERE phone IS NULL;
SELECT * FROM customers WHERE phone IS NOT NULL;

Sorting with ORDER BY

ORDER BY
-- Sort ascending (default)
SELECT name, price FROM products ORDER BY price;

-- Sort descending
SELECT name, price FROM products ORDER BY price DESC;

-- Sort by multiple columns
SELECT * FROM products
ORDER BY category ASC, price DESC;

-- NULLs go last (default is NULLS LAST in PostgreSQL for DESC)
SELECT * FROM customers
ORDER BY city NULLS LAST;

LIMIT & OFFSET (Pagination)

Pagination
-- Get only first 10 rows (like SELECT TOP 10 in SQL Server)
SELECT * FROM products ORDER BY price DESC LIMIT 10;

-- Page 2: skip first 10, get next 10 (OFFSET = skip N rows)
SELECT * FROM products ORDER BY product_id LIMIT 10 OFFSET 10;

-- Page 3:
SELECT * FROM products ORDER BY product_id LIMIT 10 OFFSET 20;

Useful String Functions

String functions
SELECT
    UPPER(first_name)                  AS upper_name,    -- PRIYA
    LOWER(email)                        AS lower_email,
    LENGTH(first_name)                 AS name_length,   -- 5
    TRIM('  hello  ')                  AS trimmed,       -- 'hello'
    SUBSTRING(email, 1, POSITION('@' IN email)-1) AS username,
    REPLACE(phone, '-', '')           AS clean_phone,
    LPAD(customer_id::TEXT, 6, '0')   AS padded_id      -- 000001
FROM customers;

DISTINCT — Remove Duplicates

DISTINCT
-- List unique cities
SELECT DISTINCT city FROM customers;

-- Count unique cities
SELECT COUNT(DISTINCT city) FROM customers;

-- Unique combinations
SELECT DISTINCT category, is_active FROM products;

UPDATE & DELETE

📖 15 min🛠 Hands-on

UPDATE — Modifying Existing Data

UPDATE examples
-- Update a single row
UPDATE customers
SET city = 'Hyderabad', phone = '+91 98765 43210'
WHERE customer_id = 1;

-- Update multiple rows matching a condition
UPDATE products
SET is_active = FALSE
WHERE stock_qty = 0;

-- Update using a calculation
UPDATE products
SET price = price * 1.10  -- 10% price increase
WHERE category = 'Electronics';

-- UPDATE with RETURNING (see what changed)
UPDATE products
SET stock_qty = stock_qty + 50
WHERE name = 'Coffee Maker'
RETURNING name, stock_qty;
⚠️

Always Use WHERE with UPDATE

An UPDATE without a WHERE clause updates EVERY row in the table. Always add a WHERE condition. Best practice: run the equivalent SELECT first to verify which rows you'll affect, then change SELECT to UPDATE.

DELETE — Removing Rows

DELETE examples
-- Delete a specific row
DELETE FROM customers WHERE customer_id = 5;

-- Delete rows matching a condition
DELETE FROM products
WHERE is_active = FALSE AND stock_qty = 0;

-- Delete with RETURNING (confirm what was deleted)
DELETE FROM orders
WHERE status = 'cancelled'
  AND order_date < NOW() - INTERVAL '1 year'
RETURNING order_id, order_date;

TRUNCATE — Fast Table Clear

TRUNCATE
-- Remove ALL rows from a table (much faster than DELETE)
TRUNCATE TABLE orders;

-- Also reset the sequence (auto-increment back to 1)
TRUNCATE TABLE orders RESTART IDENTITY;

-- Truncate multiple tables
TRUNCATE TABLE orders, customers CASCADE;
🔄

SQL Server vs PostgreSQL DELETE/TRUNCATE

PostgreSQL's TRUNCATE is transactional (can be rolled back!) unlike SQL Server. Also, PostgreSQL has no DELETE TOP(n) syntax — use a subquery or CTE with LIMIT instead.

Filtering & Sorting — Deep Dive

📖 20 min🛠 Hands-on

Advanced WHERE Conditions

Advanced filtering
-- CASE WHEN in SELECT (conditional logic)
SELECT
    name,
    price,
    CASE
        WHEN price < 1000  THEN 'Budget'
        WHEN price < 10000 THEN 'Mid-range'
        ELSE 'Premium'
    END AS price_tier
FROM products;

-- Subquery in WHERE
SELECT * FROM customers
WHERE customer_id IN (
    SELECT DISTINCT customer_id FROM orders
    WHERE total_amount > 50000
);

-- EXISTS subquery (often faster than IN for large sets)
SELECT * FROM customers c
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.status = 'delivered'
);

Date Filtering

Date queries
-- Orders from today
SELECT * FROM orders
WHERE order_date::date = CURRENT_DATE;

-- Orders in last 30 days
SELECT * FROM orders
WHERE order_date >= NOW() - INTERVAL '30 days';

-- Orders in a specific month
SELECT * FROM orders
WHERE DATE_TRUNC('month', order_date) = '2025-01-01';

-- Extract parts of a date
SELECT
    order_id,
    EXTRACT(YEAR  FROM order_date) AS order_year,
    EXTRACT(MONTH FROM order_date) AS order_month,
    EXTRACT(DOW   FROM order_date) AS day_of_week  -- 0=Sun, 6=Sat
FROM orders;

COALESCE — Handle NULLs

COALESCE & NULLIF
-- COALESCE returns the first non-NULL value (like ISNULL in SQL Server)
SELECT
    first_name,
    COALESCE(phone, 'No phone')     AS phone,
    COALESCE(city, country, 'Unknown') AS location
FROM customers;

-- NULLIF returns NULL if two values are equal (avoids division by zero)
SELECT
    total_amount / NULLIF(quantity, 0) AS unit_price
FROM orders;

Joins — Combining Tables

📖 30 min🛠 Core Skill

Joins are how you combine data from multiple tables. This is where relational databases shine.

INNER JOIN — Only Matching Rows

INNER JOIN
-- Get orders WITH customer names (only customers who have orders)
SELECT
    o.order_id,
    o.order_date,
    o.total_amount,
    o.status,
    c.first_name || ' ' || c.last_name AS customer_name,
    c.email
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id
ORDER BY o.order_date DESC;

LEFT JOIN — All from Left Table

LEFT JOIN
-- ALL customers, with their orders (NULL if no orders)
SELECT
    c.customer_id,
    c.first_name,
    c.last_name,
    COUNT(o.order_id)           AS order_count,
    COALESCE(SUM(o.total_amount), 0) AS total_spent
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.first_name, c.last_name
ORDER BY total_spent DESC;

-- Find customers with NO orders
SELECT c.* FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;

Joining 3 Tables

3-table join
-- Create order_items table first
CREATE TABLE order_items (
    item_id    SERIAL   PRIMARY KEY,
    order_id   INTEGER  NOT NULL REFERENCES orders(order_id),
    product_id INTEGER  NOT NULL REFERENCES products(product_id),
    quantity   INTEGER  NOT NULL DEFAULT 1,
    unit_price NUMERIC(10,2)
);

-- Join customers → orders → order_items → products
SELECT
    c.first_name || ' ' || c.last_name AS customer,
    o.order_id,
    p.name                              AS product,
    oi.quantity,
    oi.unit_price,
    oi.quantity * oi.unit_price         AS line_total
FROM customers   c
JOIN orders      o  ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id   = oi.order_id
JOIN products    p  ON oi.product_id = p.product_id
ORDER BY o.order_id, p.name;

Intermediate

Aggregations — GROUP BY & Analytics

📖 25 min🛠 Hands-on

Aggregate Functions

Core aggregates
-- Summary statistics on products
SELECT
    COUNT(*)                    AS total_products,
    COUNT(DISTINCT category)   AS unique_categories,
    MIN(price)                  AS cheapest,
    MAX(price)                  AS most_expensive,
    AVG(price)::NUMERIC(10,2)   AS avg_price,
    SUM(stock_qty)             AS total_stock
FROM products;

GROUP BY — Aggregate by Category

GROUP BY
-- Sales by product category
SELECT
    p.category,
    COUNT(oi.item_id)            AS items_sold,
    SUM(oi.quantity)             AS total_qty,
    SUM(oi.quantity * oi.unit_price) AS revenue,
    AVG(p.price)::NUMERIC(10,2)  AS avg_price
FROM products    p
JOIN order_items oi ON p.product_id = oi.product_id
GROUP BY p.category
ORDER BY revenue DESC;

HAVING — Filter on Aggregated Results

HAVING
-- WHERE filters BEFORE grouping, HAVING filters AFTER

-- Only categories with more than 5 products
SELECT category, COUNT(*) AS product_count
FROM products
WHERE is_active = TRUE           -- applied before grouping
GROUP BY category
HAVING COUNT(*) > 5             -- applied after grouping
ORDER BY product_count DESC;

-- Top customers who spent over ₹1,00,000
SELECT
    c.first_name || ' ' || c.last_name AS customer,
    SUM(o.total_amount) AS total_spent
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.first_name, c.last_name
HAVING SUM(o.total_amount) > 100000
ORDER BY total_spent DESC;

SQL Query Execution Order

📋

The ORDER SQL Executes (not how you write it)

1. FROM + JOIN — get the data sources    2. WHERE — filter rows    3. GROUP BY — group remaining rows    4. HAVING — filter groups    5. SELECT — pick columns    6. ORDER BY — sort    7. LIMIT/OFFSET — paginate

Indexes — Supercharge Query Speed

📖 20 min⚡ Performance

An index is like a book's table of contents — it lets PostgreSQL find rows without reading every single row in the table.

Creating Indexes

Index creation
-- Basic B-tree index (default, most common)
CREATE INDEX idx_customers_email
    ON customers(email);

-- Composite index (multiple columns)
CREATE INDEX idx_orders_customer_date
    ON orders(customer_id, order_date);

-- Unique index (ensures no duplicates + index)
CREATE UNIQUE INDEX idx_products_name
    ON products(name);

-- Partial index (only index rows matching a condition)
-- Much smaller + faster for common filtered queries
CREATE INDEX idx_active_products
    ON products(category, price)
    WHERE is_active = TRUE;

-- Create index CONCURRENTLY (no table lock — use on production!)
CREATE INDEX CONCURRENTLY idx_orders_status
    ON orders(status);

-- Drop an index
DROP INDEX idx_customers_email;

Index Types

Index TypeBest ForExample Use
B-tree (default)Equality, range, ORDER BYWHERE price > 1000, ORDER BY created_at
GINArrays, JSONB, full-text searchWHERE tags @> ARRAY['sale']
GiSTGeometric types, geographic dataPostGIS location queries

EXPLAIN ANALYZE — See the Query Plan

Query plan analysis
-- See how PostgreSQL plans to execute a query
EXPLAIN SELECT * FROM customers WHERE email = 'priya@example.com';

-- EXPLAIN ANALYZE actually runs the query and shows real timings
EXPLAIN ANALYZE
SELECT * FROM orders
WHERE customer_id = 1
  AND order_date > '2025-01-01';

-- Look for:
-- "Index Scan" = GOOD (using your index)
-- "Seq Scan"   = BAD on large tables (scanning every row)
-- "cost=..."   = estimated cost (lower = better)
-- "actual time=..." = real execution time in ms
💡

Golden Rules for Indexes

Index columns used in WHERE, JOIN ON, and ORDER BY. Don't over-index — each index slows down INSERT/UPDATE/DELETE. Prefer composite indexes to multiple single-column indexes. Use CONCURRENTLY on production to avoid locking.

Constraints — Data Integrity Rules

📖 15 min🔒 Data Quality
All constraint types
CREATE TABLE employees (
    employee_id   BIGSERIAL       PRIMARY KEY,         -- PK: unique + not null
    email         VARCHAR(255)    UNIQUE NOT NULL,       -- UNIQUE: no duplicates
    first_name    VARCHAR(100)    NOT NULL,             -- NOT NULL required
    salary        NUMERIC(12,2)   CHECK (salary >= 0),  -- CHECK: must be >= 0
    dept_id       INTEGER         REFERENCES departments(id), -- FK
    status        VARCHAR(20)     DEFAULT 'active',     -- DEFAULT value
    hire_date     DATE            DEFAULT CURRENT_DATE,
    -- Named constraint (easier to reference in errors)
    CONSTRAINT chk_status
        CHECK (status IN ('active', 'inactive', 'on_leave'))
);

-- Foreign key with ON DELETE behavior
ALTER TABLE orders
    ADD CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
    ON DELETE CASCADE   -- delete orders when customer is deleted
    ON UPDATE CASCADE;  -- update FK when PK changes
ON DELETE optionBehavior
RESTRICT (default)Error — prevents delete if child rows exist
CASCADEAutomatically deletes child rows
SET NULLSets FK column to NULL in child rows
SET DEFAULTSets FK column to its default value
NO ACTIONLike RESTRICT but checked at end of transaction

Transactions — ACID Guarantees

📖 20 min🔒 Critical

A transaction groups multiple SQL statements so they succeed or fail together. This is the foundation of data integrity.

Basic Transaction Syntax

Transaction example
-- Transfer money between accounts (classic example)
BEGIN;    -- Start transaction

    UPDATE accounts
    SET balance = balance - 5000
    WHERE account_id = 101;   -- deduct from sender

    UPDATE accounts
    SET balance = balance + 5000
    WHERE account_id = 202;   -- add to receiver

    INSERT INTO transfer_log (from_id, to_id, amount)
    VALUES (101, 202, 5000);

COMMIT;   -- All three statements succeed together

-- If anything fails, use ROLLBACK to undo everything:
BEGIN;
    UPDATE ...;
    -- Error occurs here
ROLLBACK;  -- Undo all changes in this transaction

SAVEPOINT — Partial Rollback

SAVEPOINT
BEGIN;

    INSERT INTO orders (...) VALUES (...);

    SAVEPOINT after_order;   -- Bookmark this point

    INSERT INTO order_items (...) VALUES (...);
    -- This fails!

    ROLLBACK TO after_order; -- Undo back to savepoint (order still exists)

    -- Try again with corrected data
    INSERT INTO order_items (...) VALUES (...);

COMMIT;

Isolation Levels

LevelPreventsUse When
READ COMMITTED (default)Dirty readsMost OLTP applications
REPEATABLE READDirty reads + non-repeatable readsReports, batch jobs
SERIALIZABLEAll anomalies — fully isolatedFinancial, inventory systems
Setting isolation level
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
    SELECT SUM(balance) FROM accounts;  -- consistent snapshot
COMMIT;

Views & CTEs — Reusable Queries

📖 25 min🧩 Composition

Views — Saved Queries

CREATE VIEW
-- Create a view for a commonly used report
CREATE VIEW customer_order_summary AS
SELECT
    c.customer_id,
    c.first_name || ' ' || c.last_name  AS customer_name,
    c.email,
    c.city,
    COUNT(o.order_id)                   AS total_orders,
    COALESCE(SUM(o.total_amount), 0)   AS lifetime_value,
    MAX(o.order_date)                   AS last_order_date
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.first_name, c.last_name, c.email, c.city;

-- Now use it like a table!
SELECT * FROM customer_order_summary
WHERE lifetime_value > 50000
ORDER BY lifetime_value DESC;

CTEs — Common Table Expressions

CTEs (introduced with the WITH keyword) are like temporary named queries. They make complex queries readable and maintainable.

WITH (CTE)
-- Find customers whose total spend is above average
WITH customer_spend AS (
    -- Step 1: Calculate total spend per customer
    SELECT
        c.customer_id,
        c.first_name || ' ' || c.last_name AS name,
        SUM(o.total_amount) AS total_spent
    FROM customers c
    JOIN orders o ON c.customer_id = o.customer_id
    GROUP BY c.customer_id, c.first_name, c.last_name
),
avg_spend AS (
    -- Step 2: Calculate the average
    SELECT AVG(total_spent) AS avg_val FROM customer_spend
)
-- Step 3: Find customers above average
SELECT cs.name, cs.total_spent, a.avg_val
FROM customer_spend cs, avg_spend a
WHERE cs.total_spent > a.avg_val
ORDER BY cs.total_spent DESC;

Recursive CTEs — Hierarchical Data

Recursive CTE (org chart)
-- Employee hierarchy (manager → reports)
WITH RECURSIVE org_chart AS (
    -- Base case: top-level employees (no manager)
    SELECT employee_id, name, manager_id, 0 AS level
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive case: find direct reports
    SELECT e.employee_id, e.name, e.manager_id, oc.level + 1
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.employee_id
)
SELECT
    REPEAT('  ', level) || name AS hierarchy,
    level
FROM org_chart
ORDER BY level, name;

Window Functions — Analytics Power

📖 30 min📊 Analytics

Window functions perform calculations across a set of rows related to the current row — without collapsing them like GROUP BY does. This is one of PostgreSQL's most powerful features.

ROW_NUMBER, RANK, DENSE_RANK

Ranking functions
SELECT
    name,
    category,
    price,
    ROW_NUMBER() OVER (PARTITION BY category ORDER BY price DESC) AS row_num,
    RANK()       OVER (PARTITION BY category ORDER BY price DESC) AS rank,
    DENSE_RANK() OVER (PARTITION BY category ORDER BY price DESC) AS dense_rank
FROM products
ORDER BY category, price DESC;

-- Get the #1 most expensive product in each category
WITH ranked AS (
    SELECT *, RANK() OVER (PARTITION BY category ORDER BY price DESC) AS rnk
    FROM products
)
SELECT * FROM ranked WHERE rnk = 1;

Running Totals and Moving Averages

Cumulative calculations
SELECT
    order_date::date            AS date,
    total_amount,
    -- Running total (cumulative sum)
    SUM(total_amount) OVER (
        ORDER BY order_date
    )                           AS running_total,
    -- 7-day moving average
    AVG(total_amount) OVER (
        ORDER BY order_date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    )::NUMERIC(10,2)            AS moving_avg_7d
FROM orders
ORDER BY order_date;

LAG / LEAD — Compare with Adjacent Rows

LAG & LEAD
-- Month-over-month revenue change
WITH monthly AS (
    SELECT
        DATE_TRUNC('month', order_date) AS month,
        SUM(total_amount) AS revenue
    FROM orders
    GROUP BY 1
)
SELECT
    month,
    revenue,
    LAG(revenue) OVER (ORDER BY month) AS prev_month_revenue,
    revenue - LAG(revenue) OVER (ORDER BY month) AS change,
    ROUND(
        (revenue - LAG(revenue) OVER (ORDER BY month))
        / NULLIF(LAG(revenue) OVER (ORDER BY month), 0) * 100,
        1
    ) AS pct_change
FROM monthly
ORDER BY month;

Stored Functions & Procedures

📖 20 min🔧 Programmability

Creating Functions (PL/pgSQL)

Simple function
-- Function: get full customer name
CREATE OR REPLACE FUNCTION get_full_name(p_customer_id INTEGER)
RETURNS TEXT
LANGUAGE plpgsql
AS $$
DECLARE
    v_name TEXT;
BEGIN
    SELECT first_name || ' ' || last_name
    INTO v_name
    FROM customers
    WHERE customer_id = p_customer_id;

    RETURN COALESCE(v_name, 'Customer not found');
END;
$$;

-- Call it:
SELECT get_full_name(1);   -- Returns: 'Priya Sharma'

Stored Procedures

Stored procedure
-- Procedure: place an order with transaction handling
CREATE OR REPLACE PROCEDURE place_order(
    p_customer_id  INTEGER,
    p_product_id   INTEGER,
    p_quantity     INTEGER
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_price      NUMERIC;
    v_order_id   INTEGER;
    v_total      NUMERIC;
BEGIN
    -- Get product price
    SELECT price INTO v_price
    FROM products WHERE product_id = p_product_id;

    v_total := v_price * p_quantity;

    -- Create the order
    INSERT INTO orders (customer_id, total_amount, status)
    VALUES (p_customer_id, v_total, 'pending')
    RETURNING order_id INTO v_order_id;

    -- Add order item
    INSERT INTO order_items (order_id, product_id, quantity, unit_price)
    VALUES (v_order_id, p_product_id, p_quantity, v_price);

    -- Reduce stock
    UPDATE products
    SET stock_qty = stock_qty - p_quantity
    WHERE product_id = p_product_id;

    RAISE NOTICE 'Order % created. Total: %', v_order_id, v_total;
END;
$$;

-- Call with CALL:
CALL place_order(1, 2, 3);   -- customer 1 buys 3 of product 2

RETURNS TRIGGER LANGUAGE plpgsql AS $$

JSON & JSONB — Document Storage

📖 20 min🧩 Flexible Data

PostgreSQL's JSONB type lets you store and query JSON documents efficiently. Use JSONB (not JSON) — it's stored in binary, indexed, and much faster to query.

Storing JSON Data

JSONB column
CREATE TABLE product_attributes (
    product_id   INTEGER PRIMARY KEY,
    attributes   JSONB
);

INSERT INTO product_attributes VALUES
(1, '{"color":"silver","weight":"1.8kg","warranty":"2yr","ports":["USB-C","HDMI"]}'),
(2, '{"color":"black","dpi":3200,"wireless":true,"buttons":6}');

Querying JSON

JSON operators
-- -> returns JSON, ->> returns TEXT
SELECT
    product_id,
    attributes->'color'       AS color_json,    -- "silver" (with quotes)
    attributes->>'color'      AS color_text,    -- silver (no quotes)
    attributes->>'warranty'   AS warranty
FROM product_attributes;

-- Filter by JSON value
SELECT * FROM product_attributes
WHERE attributes->>'color' = 'silver';

-- Check if JSON contains a key/value
SELECT * FROM product_attributes
WHERE attributes @> '{"wireless": true}';

-- Index JSONB for fast queries
CREATE INDEX idx_attrs_gin ON product_attributes USING GIN(attributes);

Performance & EXPLAIN — Tuning Queries

📖 25 min⚡ Production

Reading EXPLAIN Output

EXPLAIN output example
EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 1;

-- Output:
-- Index Scan using idx_orders_customer_date on orders (cost=0.29..8.31 rows=3 width=76) (actual time=0.028..0.033 rows=3 loops=1)
--   Index Cond: (customer_id = 1)
-- Planning Time: 0.073 ms
-- Execution Time: 0.051 ms   ← Fast! Index is being used ✅

Common Performance Anti-patterns

Bad vs Good patterns
-- ❌ BAD: Function on indexed column prevents index use
SELECT * FROM orders WHERE DATE(order_date) = '2025-01-15';

-- ✅ GOOD: Range query allows index scan
SELECT * FROM orders
WHERE order_date >= '2025-01-15' AND order_date < '2025-01-16';

-- ❌ BAD: Leading wildcard blocks index
SELECT * FROM customers WHERE email LIKE '%example.com';

-- ✅ GOOD: Trailing wildcard uses index
SELECT * FROM customers WHERE email LIKE 'priya%';

-- ❌ BAD: SELECT * fetches all columns unnecessarily
SELECT * FROM customers;

-- ✅ GOOD: Select only what you need
SELECT customer_id, email FROM customers;

Key Performance Views

Find slow queries
-- Find unused indexes (candidates for removal)
SELECT schemaname, tablename, indexname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY tablename;

-- Find tables with most sequential scans (missing indexes)
SELECT relname, seq_scan, idx_scan
FROM pg_stat_user_tables
WHERE seq_scan > idx_scan
ORDER BY seq_scan DESC;

-- Table sizes
SELECT
    tablename,
    pg_size_pretty(pg_total_relation_size(tablename::regclass)) AS total_size,
    pg_size_pretty(pg_relation_size(tablename::regclass)) AS table_size
FROM pg_tables
WHERE schemaname = 'public'
ORDER BY pg_total_relation_size(tablename::regclass) DESC;

Logical Replication on Cloud SQL

📖 30 min🔄 Production

Logical replication lets you stream data changes from one PostgreSQL instance (Publisher) to others (Subscribers) in real-time. This is what your project guide covers in depth.

Core Concepts

ConceptWhat It IsSQL Server Equivalent
WALWrite Ahead Log — all changes are written here firstTransaction Log
PublicationDefines which tables to replicate (on publisher)Publication + Articles
SubscriptionConnects to a publication and receives changesSubscription + Distribution Agent
Replication SlotBookmark tracking subscriber's position in WALDistribution database position pointer
LSNLog Sequence Number — position in WALLSN in SQL Server transaction log

Cloud SQL Setup (gcloud)

Enable logical decoding on publisher
gcloud sql instances patch YOUR_PUBLISHER \
  --database-flags \
  cloudsql.logical_decoding=on,\
  max_replication_slots=15,\
  max_wal_senders=15,\
  max_logical_replication_workers=10,\
  max_worker_processes=16,\
  track_commit_timestamp=on

Complete Setup (5 Steps)

Step 1: Create replication user (Publisher)
CREATE USER replicator
    WITH PASSWORD 'StrongPass123!'
    REPLICATION LOGIN
    CONNECTION LIMIT 10;

GRANT CONNECT ON DATABASE mydb TO replicator;
GRANT USAGE ON SCHEMA public TO replicator;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO replicator;
Step 2: Create publication (Publisher)
CREATE PUBLICATION pub_main
    FOR TABLE orders, customers, products
    WITH (publish = 'insert, update, delete, truncate',
          publish_via_partition_root = true);

-- Verify:
SELECT pubname, tablename FROM pg_publication_tables;
Step 3: Create matching tables (Subscriber)
-- Run exact same CREATE TABLE statements as publisher
-- Tables MUST exist before creating the subscription
CREATE TABLE customers (...);
CREATE TABLE products  (...);
CREATE TABLE orders    (...);
Step 4: Create subscription (Subscriber)
CREATE SUBSCRIPTION sub_main
    CONNECTION 'host=PUBLISHER_IP port=5432 dbname=mydb
                user=replicator password=StrongPass123! sslmode=require'
    PUBLICATION pub_main
    WITH (
        copy_data         = true,          -- copy existing data
        create_slot       = true,
        slot_name         = 'slot_main',
        streaming         = 'parallel',   -- PG17 performance
        synchronous_commit = 'off',        -- faster replication
        disable_on_error  = true           -- safety net
    );

-- Enable failover (PG17)
ALTER SUBSCRIPTION sub_main SET (failover = true);
Step 5: Monitor replication health
-- On Publisher: check slot health
SELECT slot_name, active,
    pg_size_pretty(pg_wal_lsn_diff(
        pg_current_wal_lsn(), restart_lsn
    )) AS wal_retained
FROM pg_replication_slots;

-- On Subscriber: check sync state per table
SELECT
    s.subname,
    r.relid::regclass AS table_name,
    CASE r.srsubstate
        WHEN 'r' THEN '✅ Live replication'
        WHEN 'd' THEN '📥 Copying data...'
        ELSE r.srsubstate
    END AS status
FROM pg_subscription s
JOIN pg_subscription_rel r ON r.srsubid = s.oid;
⚠️

Most Critical Risk: Inactive Replication Slots

If a subscriber goes offline, its slot continues to hold WAL on the publisher. WAL grows until the publisher disk fills and crashes. Always set max_slot_wal_keep_size=10240 as a safety net, and monitor inactive slots daily.
