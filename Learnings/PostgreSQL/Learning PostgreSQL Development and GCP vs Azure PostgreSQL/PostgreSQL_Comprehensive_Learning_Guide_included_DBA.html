What is PostgreSQL?

📖 10 min read 🎯 Foundation

PostgreSQL (pronounced post-gress-Q-L, often called Postgres) is a powerful, open-source relational database system with over 35 years of active development. It is trusted by companies like Apple, Instagram, Spotify, Reddit, and countless others.

Why PostgreSQL?

🆓

Free & Open Source

No licensing costs. Backed by a vibrant global community since 1986.

🔒

ACID Compliant

Rock-solid transactions — Atomicity, Consistency, Isolation, Durability guaranteed.

🧩

Extensible

Custom data types, functions, operators, and extensions like PostGIS, pgvector.

📊

SQL Standard

Most SQL-standard compliant RDBMS available. Your SQL skills transfer directly.

🌐

JSON & NoSQL

Full JSONB support means relational + document storage in one database.

⚡

High Performance

Parallel queries, advanced indexing (B-tree, GIN, GiST, BRIN), partitioning.

The PostgreSQL Architecture

Understanding the architecture helps you manage and troubleshoot your database. Here's the hierarchy:

1

PostgreSQL Server (Instance)

The running database server process. One server can host many databases.

2

Database

An isolated container. Each database has its own users, schemas, and tables. (e.g., myapp_db)

3

Schema

A namespace inside a database. The default schema is public. You can create schemas like sales, hr.

4

Table

Where data lives — rows and columns. Belongs to a schema. Full name: schema.table → public.orders

5

Row (Tuple)

A single record in a table. PostgreSQL calls rows "tuples" internally.

The CREATE TABLE statement defines the structure of your data. Each column has a name and a data type.

Create customers table
CREATE TABLE customers (

Create products table
CREATE TABLE products (
    product_id    SERIAL          PRIMARY KEY,

Create orders table
CREATE TABLE orders (
    order_id      SERIAL          PRIMARY KEY,
    customer_id   INTEGER         NOT NULL REFERENCES customers(customer_id),
    order_date    TIMESTAMP       DEFAULT NOW(),
    total_amount  NUMERIC(12,2)   NOT NULL DEFAULT 0,
    status        VARCHAR(50)     DEFAULT 'pending',
    notes         TEXT
);

Quick Check: What does SERIAL do in PostgreSQL?

✅ Correct! SERIAL is shorthand for an integer column backed by a sequence — equivalent to IDENTITY(1,1) in SQL Server. Each new row gets the next number automatically.
❌ Not quite. SERIAL creates an auto-incrementing integer — like IDENTITY(1,1) in SQL Server. Each INSERT gets the next number automatically.

INSERT with RETURNING

This is a powerful PostgreSQL feature with no SQL Server equivalent. You can get back the inserted row's data immediately — very useful for getting auto-generated IDs.

INSERT ... RETURNING
-- Get the new customer_id right after inserting
INSERT INTO customers (first_name, last_name, email)
VALUES ('Vikram', 'Singh', 'vikram@example.com')
RETURNING customer_id, created_at;

-- Returns:
-- customer_id |        created_at
-- ────────────+──────────────────────────
--           6 | 2025-06-18 10:30:00.123

UPSERT — INSERT or UPDATE (ON CONFLICT)

Upsert is the pattern "insert if not exists, update if it does." PostgreSQL's syntax is elegant.

ON CONFLICT (Upsert)
-- Insert, or update price/stock if product name already exists
INSERT INTO products (name, category, price, stock_qty)
VALUES ('Wireless Mouse', 'Electronics', 1199.00, 200)
ON CONFLICT (name)
DO UPDATE SET
    price     = EXCLUDED.price,
    stock_qty = EXCLUDED.stock_qty;

-- EXCLUDED refers to the row that WOULD have been inserted

-- Or: do nothing on conflict
INSERT INTO customers (email, first_name, last_name)
VALUES ('priya@example.com', 'Priya', 'S')
ON CONFLICT (email) DO NOTHING;
🔄

SQL Server MERGE vs PostgreSQL ON CONFLICT

SQL Server uses MERGE for upsert operations. PostgreSQL's INSERT ... ON CONFLICT is simpler and safer. PostgreSQL 15+ also has a MERGE statement if you prefer that syntax.

Filtering with WHERE

WHERE clause
-- Exact match

SELECT * FROM products

UPDATE & DELETE

📖 15 min🛠 Hands-on

UPDATE — Modifying Existing Data

UPDATE examples
-- Update a single row
UPDATE customers
SET city = 'Hyderabad', phone = '+91 98765 43210'
WHERE customer_id = 1;

-- Update multiple rows matching a condition
UPDATE products
SET is_active = FALSE
WHERE stock_qty = 0;

-- Update using a calculation
UPDATE products
SET price = price * 1.10  -- 10% price increase
WHERE category = 'Electronics';

-- UPDATE with RETURNING (see what changed)
UPDATE products
SET stock_qty = stock_qty + 50
WHERE name = 'Coffee Maker'
RETURNING name, stock_qty;
⚠️

Always Use WHERE with UPDATE

An UPDATE without a WHERE clause updates EVERY row in the table. Always add a WHERE condition. Best practice: run the equivalent SELECT first to verify which rows you'll affect, then change SELECT to UPDATE.

DELETE — Removing Rows

DELETE examples
-- Delete a specific row
DELETE FROM customers WHERE customer_id = 5;

-- Delete rows matching a condition
DELETE FROM products
WHERE is_active = FALSE AND stock_qty = 0;

-- Delete with RETURNING (confirm what was deleted)
DELETE FROM orders
WHERE status = 'cancelled'
  AND order_date < NOW() - INTERVAL '1 year'
RETURNING order_id, order_date;

TRUNCATE — Fast Table Clear

TRUNCATE
-- Remove ALL rows from a table (much faster than DELETE)
TRUNCATE TABLE orders;

-- Also reset the sequence (auto-increment back to 1)
TRUNCATE TABLE orders RESTART IDENTITY;

-- Truncate multiple tables
TRUNCATE TABLE orders, customers CASCADE;
🔄

SQL Server vs PostgreSQL DELETE/TRUNCATE

PostgreSQL's TRUNCATE is transactional (can be rolled back!) unlike SQL Server. Also, PostgreSQL has no DELETE TOP(n) syntax — use a subquery or CTE with LIMIT instead.

Advanced WHERE Conditions

Advanced filtering
-- CASE WHEN in SELECT (conditional logic)
SELECT
    name,
    price,
    CASE
        WHEN price < 1000  THEN 'Budget'
        WHEN price < 10000 THEN 'Mid-range'
        ELSE 'Premium'
    END AS price_tier
FROM products;

-- Subquery in WHERE
SELECT * FROM customers
WHERE customer_id IN (
    SELECT DISTINCT customer_id FROM orders
    WHERE total_amount > 50000
);

-- EXISTS subquery (often faster than IN for large sets)
SELECT * FROM customers c
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.status = 'delivered'
);

Date Filtering

Date queries
-- Orders from today
SELECT * FROM orders
WHERE order_date::date = CURRENT_DATE;

-- Orders in last 30 days
SELECT * FROM orders
WHERE order_date >= NOW() - INTERVAL '30 days';

-- Orders in a specific month
SELECT * FROM orders
WHERE DATE_TRUNC('month', order_date) = '2025-01-01';

-- Extract parts of a date
SELECT
    order_id,
    EXTRACT(YEAR  FROM order_date) AS order_year,
    EXTRACT(MONTH FROM order_date) AS order_month,
    EXTRACT(DOW   FROM order_date) AS day_of_week  -- 0=Sun, 6=Sat
FROM orders;

COALESCE — Handle NULLs

COALESCE & NULLIF
-- COALESCE returns the first non-NULL value (like ISNULL in SQL Server)
SELECT
    first_name,
    COALESCE(phone, 'No phone')     AS phone,
    COALESCE(city, country, 'Unknown') AS location
FROM customers;

-- NULLIF returns NULL if two values are equal (avoids division by zero)
SELECT
    total_amount / NULLIF(quantity, 0) AS unit_price
FROM orders;

Joins — Combining Tables

📖 30 min🛠 Core Skill

Joins are how you combine data from multiple tables. This is where relational databases shine.

INNER JOIN — Only Matching Rows

INNER JOIN
-- Get orders WITH customer names (only customers who have orders)
SELECT
    o.order_id,
    o.order_date,
    o.total_amount,
    o.status,
    c.first_name || ' ' || c.last_name AS customer_name,
    c.email
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id
ORDER BY o.order_date DESC;

LEFT JOIN — All from Left Table

LEFT JOIN
-- ALL customers, with their orders (NULL if no orders)
SELECT
    c.customer_id,
    c.first_name,
    c.last_name,
    COUNT(o.order_id)           AS order_count,
    COALESCE(SUM(o.total_amount), 0) AS total_spent
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.first_name, c.last_name
ORDER BY total_spent DESC;

-- Find customers with NO orders
SELECT c.* FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;

Joining 3 Tables

3-table join
-- Create order_items table first
CREATE TABLE order_items (
    item_id    SERIAL   PRIMARY KEY,
    order_id   INTEGER  NOT NULL REFERENCES orders(order_id),
    product_id INTEGER  NOT NULL REFERENCES products(product_id),
    quantity   INTEGER  NOT NULL DEFAULT 1,
    unit_price NUMERIC(10,2)
);

-- Join customers → orders → order_items → products
SELECT
    c.first_name || ' ' || c.last_name AS customer,
    o.order_id,
    p.name                              AS product,
    oi.quantity,
    oi.unit_price,
    oi.quantity * oi.unit_price         AS line_total
FROM customers   c
JOIN orders      o  ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id   = oi.order_id
JOIN products    p  ON oi.product_id = p.product_id
ORDER BY o.order_id, p.name;

Aggregations — GROUP BY & Analytics

📖 25 min🛠 Hands-on

Aggregate Functions

Core aggregates
-- Summary statistics on products
SELECT
    COUNT(*)                    AS total_products,
    COUNT(DISTINCT category)   AS unique_categories,
    MIN(price)                  AS cheapest,
    MAX(price)                  AS most_expensive,
    AVG(price)::NUMERIC(10,2)   AS avg_price,
    SUM(stock_qty)             AS total_stock
FROM products;

GROUP BY — Aggregate by Category

GROUP BY
-- Sales by product category
SELECT
    p.category,
    COUNT(oi.item_id)            AS items_sold,
    SUM(oi.quantity)             AS total_qty,
    SUM(oi.quantity * oi.unit_price) AS revenue,
    AVG(p.price)::NUMERIC(10,2)  AS avg_price
FROM products    p
JOIN order_items oi ON p.product_id = oi.product_id
GROUP BY p.category
ORDER BY revenue DESC;

HAVING — Filter on Aggregated Results

HAVING
-- WHERE filters BEFORE grouping, HAVING filters AFTER

-- Only categories with more than 5 products
SELECT category, COUNT(*) AS product_count
FROM products
WHERE is_active = TRUE           -- applied before grouping
GROUP BY category
HAVING COUNT(*) > 5             -- applied after grouping
ORDER BY product_count DESC;

-- Top customers who spent over ₹1,00,000
SELECT
    c.first_name || ' ' || c.last_name AS customer,
    SUM(o.total_amount) AS total_spent
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.first_name, c.last_name
HAVING SUM(o.total_amount) > 100000
ORDER BY total_spent DESC;

📋

The ORDER SQL Executes (not how you write it)

1. FROM + JOIN — get the data sources    2. WHERE — filter rows    3. GROUP BY — group remaining rows    4. HAVING — filter groups    5. SELECT — pick columns    6. ORDER BY — sort    7. LIMIT/OFFSET — paginate

Indexes — Supercharge Query Speed

📖 20 min⚡ Performance

An index is like a book's table of contents — it lets PostgreSQL find rows without reading every single row in the table.

Creating Indexes

Index creation
-- Basic B-tree index (default, most common)
CREATE INDEX idx_customers_email
    ON customers(email);

-- Composite index (multiple columns)
CREATE INDEX idx_orders_customer_date
    ON orders(customer_id, order_date);

-- Unique index (ensures no duplicates + index)
CREATE UNIQUE INDEX idx_products_name
    ON products(name);

-- Partial index (only index rows matching a condition)
-- Much smaller + faster for common filtered queries
CREATE INDEX idx_active_products
    ON products(category, price)
    WHERE is_active = TRUE;

-- Create index CONCURRENTLY (no table lock — use on production!)
CREATE INDEX CONCURRENTLY idx_orders_status
    ON orders(status);

-- Drop an index
DROP INDEX idx_customers_email;

Transactions — ACID Guarantees

📖 20 min🔒 Critical

A transaction groups multiple SQL statements so they succeed or fail together. This is the foundation of data integrity.

Basic Transaction Syntax

Transaction example
-- Transfer money between accounts (classic example)
BEGIN;    -- Start transaction

    UPDATE accounts
    SET balance = balance - 5000
    WHERE account_id = 101;   -- deduct from sender

    UPDATE accounts
    SET balance = balance + 5000
    WHERE account_id = 202;   -- add to receiver

    INSERT INTO transfer_log (from_id, to_id, amount)
    VALUES (101, 202, 5000);

COMMIT;   -- All three statements succeed together

-- If anything fails, use ROLLBACK to undo everything:
BEGIN;
    UPDATE ...;
    -- Error occurs here
ROLLBACK;  -- Undo all changes in this transaction

SAVEPOINT — Partial Rollback

SAVEPOINT
BEGIN;

    INSERT INTO orders (...) VALUES (...);

    SAVEPOINT after_order;   -- Bookmark this point

    INSERT INTO order_items (...) VALUES (...);
    -- This fails!

    ROLLBACK TO after_order; -- Undo back to savepoint (order still exists)

    -- Try again with corrected data
    INSERT INTO order_items (...) VALUES (...);

COMMIT;

CREATE VIEW customer_order_summary AS

    c.customer_id,

    c.city,

CTEs — Common Table Expressions

CTEs (introduced with the WITH keyword) are like temporary named queries. They make complex queries readable and maintainable.

WITH (CTE)
-- Find customers whose total spend is above average
WITH customer_spend AS (
    -- Step 1: Calculate total spend per customer
    SELECT
        c.customer_id,
        c.first_name || ' ' || c.last_name AS name,
        SUM(o.total_amount) AS total_spent
    FROM customers c
    JOIN orders o ON c.customer_id = o.customer_id
    GROUP BY c.customer_id, c.first_name, c.last_name
),
avg_spend AS (
    -- Step 2: Calculate the average
    SELECT AVG(total_spent) AS avg_val FROM customer_spend
)
-- Step 3: Find customers above average
SELECT cs.name, cs.total_spent, a.avg_val
FROM customer_spend cs, avg_spend a
WHERE cs.total_spent > a.avg_val
ORDER BY cs.total_spent DESC;

Recursive CTEs — Hierarchical Data

Recursive CTE (org chart)
-- Employee hierarchy (manager → reports)
WITH RECURSIVE org_chart AS (
    -- Base case: top-level employees (no manager)
    SELECT employee_id, name, manager_id, 0 AS level
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive case: find direct reports
    SELECT e.employee_id, e.name, e.manager_id, oc.level + 1
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.employee_id
)
SELECT
    REPEAT('  ', level) || name AS hierarchy,
    level
FROM org_chart
ORDER BY level, name;

Window Functions — Analytics Power

📖 30 min📊 Analytics

Window functions perform calculations across a set of rows related to the current row — without collapsing them like GROUP BY does. This is one of PostgreSQL's most powerful features.

ROW_NUMBER, RANK, DENSE_RANK

Ranking functions
SELECT
    name,
    category,
    price,
    ROW_NUMBER() OVER (PARTITION BY category ORDER BY price DESC) AS row_num,
    RANK()       OVER (PARTITION BY category ORDER BY price DESC) AS rank,
    DENSE_RANK() OVER (PARTITION BY category ORDER BY price DESC) AS dense_rank
FROM products
ORDER BY category, price DESC;

-- Get the #1 most expensive product in each category
WITH ranked AS (
    SELECT *, RANK() OVER (PARTITION BY category ORDER BY price DESC) AS rnk
    FROM products
)
SELECT * FROM ranked WHERE rnk = 1;

Running Totals and Moving Averages

Cumulative calculations
SELECT
    order_date::date            AS date,
    total_amount,
    -- Running total (cumulative sum)
    SUM(total_amount) OVER (
        ORDER BY order_date
    )                           AS running_total,
    -- 7-day moving average
    AVG(total_amount) OVER (
        ORDER BY order_date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    )::NUMERIC(10,2)            AS moving_avg_7d
FROM orders
ORDER BY order_date;

LAG / LEAD — Compare with Adjacent Rows

LAG & LEAD
-- Month-over-month revenue change
WITH monthly AS (
    SELECT
        DATE_TRUNC('month', order_date) AS month,
        SUM(total_amount) AS revenue
    FROM orders
    GROUP BY 1
)
SELECT
    month,
    revenue,
    LAG(revenue) OVER (ORDER BY month) AS prev_month_revenue,
    revenue - LAG(revenue) OVER (ORDER BY month) AS change,
    ROUND(
        (revenue - LAG(revenue) OVER (ORDER BY month))
        / NULLIF(LAG(revenue) OVER (ORDER BY month), 0) * 100,
        1
    ) AS pct_change
FROM monthly
ORDER BY month;

Stored procedure
-- Procedure: place an order with transaction handling
CREATE OR REPLACE PROCEDURE place_order(
    p_customer_id  INTEGER,
    p_product_id   INTEGER,
    p_quantity     INTEGER
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_price      NUMERIC;
    v_order_id   INTEGER;
    v_total      NUMERIC;
BEGIN
    -- Get product price
    SELECT price INTO v_price
    FROM products WHERE product_id = p_product_id;

    v_total := v_price * p_quantity;

    -- Create the order
    INSERT INTO orders (customer_id, total_amount, status)
    VALUES (p_customer_id, v_total, 'pending')
    RETURNING order_id INTO v_order_id;

    -- Add order item
    INSERT INTO order_items (order_id, product_id, quantity, unit_price)
    VALUES (v_order_id, p_product_id, p_quantity, v_price);

    -- Reduce stock
    UPDATE products
    SET stock_qty = stock_qty - p_quantity
    WHERE product_id = p_product_id;

    RAISE NOTICE 'Order % created. Total: %', v_order_id, v_total;
END;
$$;

CALL place_order(1, 2, 3);   -- customer 1 buys 3 of product 2

CREATE SUBSCRIPTION sub_main
    CONNECTION 'host=PUBLISHER_IP port=5432 dbname=mydb
                user=replicator password=StrongPass123! sslmode=require'
    PUBLICATION pub_main
    WITH (
        copy_data         = true,          -- copy existing data
        create_slot       = true,
        slot_name         = 'slot_main',
        streaming         = 'parallel',   -- PG17 performance
        synchronous_commit = 'off',        -- faster replication
        disable_on_error  = true           -- safety net

-- On Publisher: check slot health
SELECT slot_name, active,
    pg_size_pretty(pg_wal_lsn_diff(

SELECT

    r.relid::regclass AS table_name,

        WHEN 'r' THEN '✅ Live replication'
        WHEN 'd' THEN '📥 Copying data...'
        ELSE r.srsubstate
    END AS status
FROM pg_subscription s
JOIN pg_subscription_rel r ON r.srsubid = s.oid;

Table Partitioning

📖 25 min⚡ Scalability

Partitioning splits a large table into smaller physical pieces (partitions) while still presenting it as one logical table. Queries only scan relevant partitions — dramatically faster on billion-row tables.

When to Partition

💡

Rule of Thumb

Consider partitioning when a table exceeds ~50–100 million rows, queries almost always filter on one column (date, region, status), or you regularly archive/drop old data. Below that threshold, a good index is simpler and faster.

Range Partitioning — by Date

Most common pattern — partition orders, logs, or events by month or year.

Range partitioning by month
-- 1. Create the partitioned parent table
CREATE TABLE orders_partitioned (
    order_id      BIGSERIAL,
    customer_id   INTEGER       NOT NULL,
    order_date    TIMESTAMPTZ   NOT NULL,
    total_amount  NUMERIC(12,2),
    status        VARCHAR(50)
) PARTITION BY RANGE (order_date);

-- 2. Create individual partitions
CREATE TABLE orders_2024_q1 PARTITION OF orders_partitioned
    FOR VALUES FROM ('2024-01-01') TO ('2024-04-01');

CREATE TABLE orders_2024_q2 PARTITION OF orders_partitioned
    FOR VALUES FROM ('2024-04-01') TO ('2024-07-01');

CREATE TABLE orders_2024_q3 PARTITION OF orders_partitioned
    FOR VALUES FROM ('2024-07-01') TO ('2024-10-01');

CREATE TABLE orders_2024_q4 PARTITION OF orders_partitioned
    FOR VALUES FROM ('2024-10-01') TO ('2025-01-01');

-- 3. Add indexes ON EACH PARTITION (or the parent)
CREATE INDEX ON orders_partitioned (customer_id, order_date);

-- 4. Query as normal — PostgreSQL auto-routes to correct partition
SELECT * FROM orders_partitioned
WHERE order_date >= '2024-06-01' AND order_date < '2024-07-01';
-- Only scans orders_2024_q2 — ignores all other partitions ✅

Row-Level Security (RLS)

📖 20 min🔒 Security

Row-Level Security lets you control which rows a user can see or modify — enforced at the database level, not the application level. Perfect for multi-tenant apps where each user should only see their own data.

Why RLS Matters

🏢

Multi-tenant SaaS

Tenant A can never accidentally see Tenant B's data — even with a buggy query.

🛡️

Defense in Depth

Even if app code has a bug, the DB enforces access rules independently.

✅

Compliance

GDPR, HIPAA, and SOC2 auditors love database-level access controls.

Enable RLS and Create Policies

Basic RLS setup
-- 1. Enable RLS on the table
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- 2. Create a policy: users can only see their OWN orders
CREATE POLICY orders_isolation ON orders
    USING (customer_id = current_setting('app.current_user_id')::INTEGER);

-- 3. In your application, set the context before querying:
SET app.current_user_id = '42';
SELECT * FROM orders;  -- automatically filtered to customer_id = 42

Multi-tenant App — Full Example

Multi-tenant RLS
-- Add tenant_id to every table
ALTER TABLE customers ADD COLUMN tenant_id INTEGER;
ALTER TABLE orders     ADD COLUMN tenant_id INTEGER;

-- Enable RLS
ALTER TABLE customers ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders     ENABLE ROW LEVEL SECURITY;

-- Separate SELECT and INSERT/UPDATE policies
CREATE POLICY tenant_isolation_customers ON customers
    USING (tenant_id = current_setting('app.tenant_id')::INTEGER)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::INTEGER);
-- USING  = filter on SELECT/UPDATE/DELETE
-- WITH CHECK = validate on INSERT/UPDATE

-- Superusers bypass RLS by default. Force RLS even for table owner:
ALTER TABLE customers FORCE ROW LEVEL SECURITY;

-- Create a DB role for your app (never use superuser in app code!)
CREATE ROLE app_user LOGIN PASSWORD 'AppPass123!';
GRANT SELECT, INSERT, UPDATE, DELETE ON customers, orders TO app_user;

Node.js / Python Integration

Node.js — set tenant context before query
// In your API handler (Node.js with pg library)
async function getOrders(tenantId, userId) {
  const client = await pool.connect();
  try {
    // Set RLS context for this transaction
    await client.query(`SET LOCAL app.tenant_id = $1`, [tenantId]);
    await client.query(`SET LOCAL app.current_user_id = $1`, [userId]);

    // This query is automatically filtered by RLS
    const result = await client.query(`SELECT * FROM orders`);
    return result.rows;  // only this tenant's orders
  } finally {
    client.release();
  }
}
⚠️

Critical: Use SET LOCAL not SET

SET LOCAL scopes the setting to the current transaction only. SET persists for the entire session. In connection pools, sessions are reused — always use SET LOCAL inside a transaction to avoid tenant data leakage between requests.

MVCC — How PostgreSQL Handles Concurrency

📖 35 min🔬 Deep Internals

MVCC — Multi-Version Concurrency Control — is the single most important concept in PostgreSQL internals. It explains why readers never block writers, why dead rows accumulate, why VACUUM exists, and how transaction isolation actually works. Everything else in production operations flows from this.

The Core Insight

PostgreSQL never modifies a row in place. When you UPDATE a row, PostgreSQL writes a brand new version of the row and marks the old version as expired. Both versions exist on disk simultaneously. Different transactions see different versions depending on when their snapshot was taken.

🧠

Why this matters

Because readers see their own consistent snapshot and writers write new versions, reads and writes never block each other. This is fundamentally different from SQL Server’s default locking model, where readers and writers contend for the same locks.

Hidden System Columns on Every Row

Inspect MVCC columns
-- Every row carries hidden MVCC metadata
SELECT
    ctid,   -- physical location (page, slot) e.g. (0,1)
    xmin,   -- transaction ID that CREATED this row version
    xmax,   -- transaction ID that DELETED/UPDATED it (0 = still live)
    *
FROM orders LIMIT 5;
-- ctid | xmin | xmax | order_id | status
-- (0,1)|  542 |    0 |        1 | pending  <-- live row: xmax=0
-- (0,2)|  543 |  548 |        2 | shipped  <-- dead row: updated by txn 548

What UPDATE Actually Does

Two rows now exist on disk
UPDATE orders SET status = 'shipped' WHERE order_id = 1;
-- AFTER: TWO rows exist simultaneously
-- ctid  | xmin | xmax | status
-- (0,1) |  542 |  601 | pending  <-- OLD version: xmax=601 marks it expired
-- (0,4) |  601 |    0 | shipped  <-- NEW version: created by txn 601
-- Row (0,1) is a DEAD TUPLE: invisible to new transactions
-- but physically on disk consuming space until VACUUM cleans it

Snapshot Isolation in Action

Concurrent snapshot demo
-- SESSION A: snapshot taken at BEGIN
BEGIN;
SELECT status FROM orders WHERE order_id = 1; -- Returns: pending
-- SESSION B commits an update while A is running
-- SESSION A queries again:
SELECT status FROM orders WHERE order_id = 1;
-- READ COMMITTED: returns 'shipped' (re-read sees committed data)
-- REPEATABLE READ: returns 'pending' (snapshot is fixed at BEGIN)
-- This is why isolation level choice matters for business logic
COMMIT;

Dead Tuples and VACUUM

Every UPDATE and DELETE leaves dead tuples consuming disk space. VACUUM reclaims this space. Without it, tables bloat indefinitely and queries slow down.

Monitor and tune VACUUM
-- Monitor dead tuple buildup
SELECT relname, n_live_tup, n_dead_tup,
    ROUND(n_dead_tup * 100.0 / NULLIF(n_live_tup+n_dead_tup,0),1) AS dead_pct,
    last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;
-- dead_pct > 20% = table needs attention

-- Tune autovacuum for high-churn tables
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor  = 0.01,  -- trigger at 1% dead (default 20%)
    autovacuum_analyze_scale_factor = 0.005  -- analyze at 0.5% change
);

-- Monitor transaction ID wraparound (alert if age > 500M)
-- PostgreSQL shuts down at 2.1 billion to prevent corruption
SELECT relname, age(relfrozenxid) AS xid_age,
    2100000000 - age(relfrozenxid) AS txns_remaining
FROM pg_class WHERE relkind = 'r'
ORDER BY xid_age DESC LIMIT 10;

HOT Updates — The Performance Optimization Inside MVCC

Normal UPDATEs always write a new row version to a potentially different page, requiring an index entry update for every index on the table. HOT (Heap-Only Tuple) updates are a special fast path: if the updated columns are not part of any index, and the new version fits on the same page, PostgreSQL can skip updating all indexes and instead chain the old and new version with a pointer. This is dramatically faster on heavily indexed, frequently updated tables.

Check HOT update ratio
-- High n_tup_hot_upd means HOT is working well (good)
SELECT
    relname,
    n_tup_upd        AS total_updates,
    n_tup_hot_upd    AS hot_updates,
    ROUND(n_tup_hot_upd * 100.0 / NULLIF(n_tup_upd,0), 1) AS hot_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 0
ORDER BY n_tup_upd DESC;
-- hot_pct near 100% = great. Near 0% = every update rewrites all indexes.
-- If hot_pct is low on a table you update frequently, check:
-- 1. Are you updating indexed columns? (unavoidable if so)
-- 2. Is fillfactor too high? (rows can't fit on same page)

-- Improve HOT ratio: leave room on each page for in-place updates
ALTER TABLE orders SET (fillfactor = 70);
-- Pages only 70% full at load time, leaving 30% for HOT updates
VACUUM FULL orders; -- restructure existing pages (full lock — run off-peak)

Table Bloat — Measuring and Fixing It

Over time, high-write tables accumulate dead tuples that VACUUM has not yet reclaimed. This is called bloat: the table is physically larger than its live data requires, which means more pages to read on every sequential scan. Bloat above 30% is a problem worth fixing.

Estimate table bloat
-- Quick bloat estimate: compare physical size to expected live data size
SELECT
    schemaname,
    tablename,
    pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS total_size,
    n_live_tup,
    n_dead_tup,
    ROUND(n_dead_tup * 100.0 / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
    last_autovacuum::date,
    last_autoanalyze::date
FROM pg_stat_user_tables
WHERE schemaname = 'public'
ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC;

-- Fix options (choose based on urgency and downtime tolerance):
VACUUM        orders;  -- marks dead space as reusable, NO lock, no shrink
VACUUM ANALYZE orders; -- vacuum + update statistics in one pass
VACUUM FULL   orders;  -- rewrites table, reclaims disk, ACCESS EXCLUSIVE lock
                         -- alternative: pg_repack extension (no lock, prefer in prod)

Transaction ID Wraparound — The Silent Time Bomb

PostgreSQL transaction IDs (xid) are 32-bit integers. After 2.1 billion transactions, they wrap around to zero. PostgreSQL prevents this by running VACUUM FREEZE on old rows, replacing their xmin with a special frozen marker meaning "visible to all transactions forever." If this freezing falls too far behind, PostgreSQL will refuse all new writes and force an emergency autovacuum — an outage.

Monitor wraparound risk — add this to your daily alert queries
-- CRITICAL monitoring query: alert if age > 500 million
SELECT
    relname,
    age(relfrozenxid)                              AS xid_age,
    2100000000 - age(relfrozenxid)                AS xids_until_danger,
    pg_size_pretty(pg_total_relation_size(oid))   AS table_size
FROM pg_class
WHERE relkind = 'r'
  AND age(relfrozenxid) > 200000000  -- warn at 200M (10% of danger zone)
ORDER BY xid_age DESC;
-- xid_age > 1.5 billion: EMERGENCY — schedule immediate VACUUM FREEZE
-- xid_age > 2 billion:   PostgreSQL shuts down writes automatically

-- Force freeze on a specific table (safe, runs online)
VACUUM FREEZE orders;
⚠️

The Production Scenario That Kills Databases

A long-running transaction (hours) holds a snapshot that prevents VACUUM from advancing the freeze horizon across the entire database. Replication slots with inactive subscribers do the same thing. Monitor both: SELECT now() - xact_start FROM pg_stat_activity ORDER BY xact_start LIMIT 5 and SELECT slot_name, age(xmin) FROM pg_replication_slots.

WAL Internals — Write-Ahead Log Deep Dive

📖 30 min🔬 Deep Internals

The WAL is the most important file in PostgreSQL. It is the source of durability, the basis of replication, and the mechanism for crash recovery. Understanding it lets you reason about every durability and performance trade-off in the system.

Why Write-Ahead?

Random disk writes are slow. PostgreSQL instead writes a small sequential WAL record first (fast), confirms the transaction, then flushes actual data pages to disk in batches. If the system crashes, the WAL record is replayed on restart. Sequential writes are 10–100x faster than random writes — this is the performance foundation of PostgreSQL’s durability model.

🧠

The Durability Guarantee

A transaction is durable the moment its WAL record is flushed to disk — not when the data page hits disk. This is why synchronous_commit = off creates a small durability window: the application gets its confirmation before the WAL is synced. A crash in the next ~200ms could lose the last few transactions.

Checkpoints

A checkpoint is when PostgreSQL systematically flushes all dirty (modified) data pages from memory to disk. This limits how much WAL must be replayed during crash recovery. Checkpoints happen on a schedule or when WAL exceeds max_wal_size.

WAL and checkpoint monitoring
-- Monitor checkpoint health
SELECT
    checkpoints_timed,      -- normal scheduled checkpoints
    checkpoints_req,        -- forced by max_wal_size -- HIGH = problem
    checkpoint_write_time,  -- ms writing dirty pages
    checkpoint_sync_time,   -- ms fsyncing to disk
    buffers_checkpoint,     -- pages written at checkpoints
    buffers_backend         -- pages written directly by query backends -- HIGH = problem
FROM pg_stat_bgwriter;

-- Key WAL configuration
SHOW max_wal_size;                  -- WAL growth before forced checkpoint (default 1GB)
SHOW checkpoint_completion_target;  -- spread writes over this fraction (default 0.9)
SHOW wal_buffers;                   -- WAL buffer in shared memory (default 16MB)
SHOW full_page_writes;              -- must be ON -- crash safety for 8KB pages

-- How much WAL retained per replication slot
SELECT slot_name, active,
    pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_retained
FROM pg_replication_slots;
⚠️

Never disable full_page_writes on production

PostgreSQL pages are 8KB. OS blocks are typically 4KB. A crash mid-write leaves a half-written page. With full_page_writes = on, PostgreSQL writes the full old page to WAL before modifying it after each checkpoint — enabling complete recovery. On Cloud SQL this is always enabled and cannot be disabled.

LSN — Log Sequence Number Anatomy

Every byte in the WAL has a unique address called an LSN (Log Sequence Number). It looks like 0/1A2B3C40 — two hex numbers separated by a slash. The first part is the WAL segment file number; the second is the byte offset within that segment. LSNs let replication subscribers say exactly which WAL position they've consumed up to.

Working with LSNs
-- Current WAL write position
SELECT pg_current_wal_lsn();       -- e.g. 0/1A2B3C40

-- How much WAL has been written since last checkpoint
SELECT pg_size_pretty(
    pg_wal_lsn_diff(pg_current_wal_lsn(),
                    (SELECT redo_lsn FROM pg_control_checkpoint()))
) AS wal_since_checkpoint;

-- Replication lag in bytes AND time
SELECT
    client_addr,
    state,
    pg_size_pretty(pg_wal_lsn_diff(
        sent_lsn, replay_lsn))  AS replay_lag_bytes,
    replay_lag                   AS replay_lag_time,
    sent_lsn,
    replay_lsn
FROM pg_stat_replication;

-- Identify which WAL file an LSN is in
SELECT pg_walfile_name(pg_current_wal_lsn());
-- Returns: 00000001000000000000001A
-- Naming: timeline(8) + segment_hi(8) + segment_lo(8)
-- WAL files live in: $PGDATA/pg_wal/ (not directly accessible on Cloud SQL)

How Crash Recovery Works

When PostgreSQL starts after a crash, it checks the WAL for records written after the last checkpoint's redo LSN. Every such record is replayed against the data files in order. When replay is complete, the database opens. This is why checkpoint frequency matters: more frequent checkpoints = less WAL to replay = faster recovery time.

Query Planner and Cost Model

📖 35 min⚡ Performance Foundation

When you run a query, PostgreSQL generates many possible execution plans, estimates the cost of each, and picks the cheapest. Understanding this cost model lets you guide the planner instead of fighting it.

What the Planner Knows — Statistics

Inspect column statistics

    correlation,    -- physical order correlation (1.0 = index scan is very fast)
    most_common_vals
FROM pg_stats WHERE tablename = 'orders';

ANALYZE orders;

ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;
ANALYZE orders;

The Cost Model

Cost parameters and SSD tuning
-- Cost is a unitless estimate. Key parameters:

SHOW random_page_cost; -- random page read (default: 4.0)
SHOW cpu_tuple_cost;   -- per-row processing (default: 0.01)

-- WHY the planner sometimes chooses Seq Scan over an Index Scan:
-- If the query returns >5-10% of rows, random I/O for the index
-- is MORE expensive than a sequential full table scan.
-- On SSDs, random vs sequential penalty is much smaller:
SET random_page_cost = 1.1;
-- gcloud sql instances patch INSTANCE --database-flags random_page_cost=1.1

The Actual Cost Formula

The planner estimates: cost = pages × page_cost + rows × cpu_cost. For a sequential scan: relpages × seq_page_cost + reltuples × cpu_tuple_cost. For an index scan: leaf_pages × random_page_cost + matched_rows × cpu_index_tuple_cost + matched_rows × cpu_tuple_cost. The planner chooses whichever total is lower. Understanding this explains every surprising plan choice — when 5% of rows are returned, the index beats a seq scan; at 30%+ the seq scan usually wins because sequential reads are far cheaper than random ones.

FROM pg_class WHERE relname = 'orders';

TOAST and the Storage Engine

📖 20 min🔬 Storage Internals

TOAST (The Oversized-Attribute Storage Technique) is how PostgreSQL stores column values larger than 8KB. It explains many surprising performance behaviors around TEXT, JSONB, and BYTEA columns.

🧠

8KB Pages — Everything Flows From This

PostgreSQL stores all data in fixed 8KB pages. One row must fit on a single page. If any column value exceeds roughly 2KB, PostgreSQL automatically compresses or moves it to a separate hidden TOAST table. You never invoke this explicitly — it happens transparently behind every TEXT and JSONB column you create.

    CASE attstorage
        WHEN 'x' THEN 'EXTENDED'
        WHEN 'e' THEN 'EXTERNAL'
        WHEN 'm' THEN 'MAIN'
        WHEN 'p' THEN 'PLAIN'

FROM pg_attribute
WHERE attrelid = 'orders'::regclass AND attnum > 0 AND NOT attisdropped;
⚠️

Why SELECT * on JSONB tables is slow

When a JSONB column is TOASTed (stored out-of-line), fetching it requires a second random lookup into the TOAST table for each row. Selecting 10,000 rows with large JSONB columns = 10,000 extra disk reads. Always select only the keys you need: attributes->>'color' instead of the whole column.

Normalization — 1NF Through BCNF

📖 40 min🏗️ Foundation Skill

Normalization is the set of rules for eliminating data redundancy and preventing update anomalies. Bad normalization compounds into unmaintainable schemas over months and years. This is the most important design skill for a core PostgreSQL developer.

The Three Anomalies Bad Design Creates

🔄

Update anomaly

Change a fact in one place, forget to change it in 10,000 other copies. Database now has contradictory data.

❌

Insertion anomaly

Cannot insert a valid fact without having unrelated data. Cannot add a product category until at least one product exists.

🗑️

Deletion anomaly

Deleting one fact accidentally destroys another. Deleting the last order from a customer also deletes their city information.

First Normal Form — Atomic Values

1NF: no multi-values, no repeating groups
-- VIOLATES 1NF: comma-separated phones not atomic
-- customer_id | phone_numbers: '+91 98765, +91 87654'

-- FIX: separate table per multi-valued attribute
CREATE TABLE customer_phones (
    phone_id    BIGSERIAL   PRIMARY KEY,
    customer_id INTEGER     NOT NULL REFERENCES customers,
    phone       VARCHAR(20) NOT NULL,
    type        TEXT        DEFAULT 'mobile'
);

Second Normal Form — No Partial Dependencies

2NF: every non-key column must depend on the WHOLE primary key
-- VIOLATES 2NF: composite PK is (order_id, product_id)
-- but product_name depends only on product_id, not the full PK

-- FIX: product_name belongs only in the products table
CREATE TABLE products    (product_id BIGSERIAL PRIMARY KEY, name TEXT, ...);
CREATE TABLE order_items (
    order_id   INTEGER       REFERENCES orders,
    product_id INTEGER       REFERENCES products,
    quantity   INTEGER       NOT NULL,
    unit_price NUMERIC(10,2) NOT NULL, -- price at time of order: OK here
    PRIMARY KEY (order_id, product_id)
);

Third Normal Form — No Transitive Dependencies

3NF: no non-key column depends on another non-key column
-- VIOLATES 3NF: customer_id -> zip_code -> city -> state (transitive)
-- city and state depend on zip_code, not on customer_id directly

-- FIX: zip codes in their own reference table
CREATE TABLE zip_codes (zip_code VARCHAR(10) PRIMARY KEY, city TEXT, state TEXT);
CREATE TABLE customers  (customer_id BIGSERIAL PRIMARY KEY, name TEXT,
    zip_code VARCHAR(10) REFERENCES zip_codes
-- Now city and state are stored ONCE for all 10,000 customers in 500001
);

When to Intentionally Denormalize

⚠️

Always normalize first. Denormalize only with proof.

Denormalize only when: you have a measured performance problem, joins are the proven bottleneck via EXPLAIN, and you accept the consistency maintenance burden. Common valid denormalizations: cached order totals (avoid summing order_items on every request), materialized views for heavy dashboards, storing price on order_items to preserve historical pricing.

Materialized view as deliberate denormalization
CREATE MATERIALIZED VIEW customer_stats AS
SELECT customer_id,
    COUNT(*) AS order_count,
    SUM(total_amount) AS lifetime_value
FROM orders GROUP BY customer_id;
CREATE UNIQUE INDEX ON customer_stats(customer_id);
-- Refresh without locking reads:
REFRESH MATERIALIZED VIEW CONCURRENTLY customer_stats;

Category tree with recursive CTE
CREATE TABLE categories (

);
WITH RECURSIVE tree AS (
    SELECT category_id, name, 0 AS depth FROM categories WHERE parent_id IS NULL
    UNION ALL
    SELECT c.category_id, c.name, t.depth+1
    FROM categories c JOIN tree t ON c.parent_id = t.category_id
)
SELECT REPEAT('  ', depth) || name AS tree FROM tree;

Track every INSERT/UPDATE/DELETE

    table_name TEXT        NOT NULL,
    record_id  BIGINT      NOT NULL,
    operation  TEXT        NOT NULL CHECK(operation IN('INSERT','UPDATE','DELETE')),
    old_data   JSONB,
    new_data   JSONB,
    changed_by TEXT        DEFAULT current_user,

CREATE OR REPLACE FUNCTION audit_fn() RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO audit_log(table_name,record_id,operation,old_data,new_data)
    VALUES(TG_TABLE_NAME,COALESCE(NEW.id,OLD.id)::BIGINT,TG_OP,

        CASE WHEN TG_OP='DELETE' THEN NULL ELSE row_to_json(NEW)::JSONB END);
    RETURN COALESCE(NEW,OLD);
END; $$;

The Most Dangerous Production Pattern

ACCESS EXCLUSIVE blocks ALL queries including simple SELECTs. ALTER TABLE orders ADD COLUMN notes TEXT NOT NULL DEFAULT '' takes ACCESS EXCLUSIVE and rewrites the entire table. Monitoring Active Locks

Who is blocking whom right now
SELECT
    wait.pid,
    wait.query                       AS waiting_query,
    block.pid                        AS blocking_pid,
    block.query                      AS blocking_query,
    NOW() - wait.query_start        AS waiting_for
FROM pg_stat_activity wait
JOIN pg_stat_activity block
    ON block.pid = ANY(pg_blocking_pids(wait.pid))
WHERE wait.wait_event_type = 'Lock'
ORDER BY waiting_for DESC;

SELECT FOR UPDATE Patterns

Row-level locking and job queues
-- Pessimistic locking: lock rows before read-modify-write
BEGIN;
SELECT stock_qty FROM products WHERE product_id = 1 FOR UPDATE;
UPDATE products SET stock_qty = stock_qty - 1 WHERE product_id = 1 AND stock_qty > 0;
COMMIT;

-- Job queue: skip locked rows, grab first available job
SELECT * FROM job_queue WHERE status = 'pending'
ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED;

-- Fail immediately if row is locked (no waiting)
SELECT * FROM orders WHERE order_id = 1 FOR UPDATE NOWAIT;

Deadlock Prevention

The golden rule: always lock in the same order
-- DEADLOCK: Session A locks row 1 then waits for row 2
--           Session B locks row 2 then waits for row 1
-- PostgreSQL detects and kills one: "ERROR: deadlock detected"

-- PREVENTION: acquire multiple row locks in a CONSISTENT ORDER
SELECT * FROM orders
WHERE order_id = ANY(ARRAY[1,2])
ORDER BY order_id -- same order in ALL sessions = no deadlock
FOR UPDATE;

-- Advisory locks: named application-level distributed locking
SELECT pg_try_advisory_lock(12345);   -- returns true/false immediately
SELECT pg_advisory_unlock(12345);     -- release when done
-- Use for: preventing duplicate cron job runs across app servers

Lock Timeouts — Protecting Production from Lock Queues

When a lock cannot be acquired, PostgreSQL waits indefinitely by default. In production, a migration waiting for a lock silently blocks all subsequent queries that need the same table. Two settings prevent this from causing cascading incidents.

Timeout settings every production migration needs
-- lock_timeout: fail immediately if the lock cannot be acquired within N ms
-- This prevents your migration from sitting in the lock queue and blocking everything
SET lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN notes TEXT;
-- If another transaction holds a conflicting lock:
-- ERROR: canceling statement due to lock timeout
-- Safe outcome: your migration failed cleanly, nothing was blocked

-- statement_timeout: kill any query that runs longer than N ms
-- Prevents runaway analytical queries from holding locks
SET statement_timeout = '30s';
-- Set globally via Cloud SQL flag: statement_timeout = 30000 (milliseconds)
-- Override per-session for migrations: SET LOCAL statement_timeout = '0';

-- idle_in_transaction_session_timeout: kill sessions that hold open transactions
-- An idle open transaction blocks VACUUM and holds locks
SET idle_in_transaction_session_timeout = '10min';

Safe DDL Patterns — Zero-Downtime Schema Changes

The correct 3-step pattern for adding NOT NULL columns
-- WRONG: One command, rewrites table, holds ACCESS EXCLUSIVE for minutes
ALTER TABLE orders ADD COLUMN notes TEXT NOT NULL DEFAULT '';

-- CORRECT: Three steps, each fast, minimal lock duration

-- Step 1: Add nullable column (fast — just metadata change in PG11+)
ALTER TABLE orders ADD COLUMN notes TEXT;

-- Step 2: Backfill in batches (no table lock, can run for hours)
UPDATE orders SET notes = ''
WHERE ctid = ANY(ARRAY(
    SELECT ctid FROM orders WHERE notes IS NULL LIMIT 10000
));
-- Repeat until no rows remain (run from application code or scheduled job)

-- Step 3: Add NOT NULL constraint — PostgreSQL verifies in place (PG17: fast)
-- Use NOT VALID to skip validation, then validate separately
ALTER TABLE orders
    ADD CONSTRAINT orders_notes_not_null CHECK (notes IS NOT NULL) NOT VALID;
ALTER TABLE orders
    VALIDATE CONSTRAINT orders_notes_not_null;
-- VALIDATE acquires SHARE UPDATE EXCLUSIVE (allows reads and writes)

-- Index that doesn't block production:
-- CREATE INDEX CONCURRENTLY (no lock, slower, can fail — check pg_stat_progress_create_index)
CREATE INDEX CONCURRENTLY idx_orders_customer
    ON orders(customer_id);
SELECT phase, blocks_done, blocks_total
FROM pg_stat_progress_create_index;

Advisory locks are application-managed locks stored in PostgreSQL that don't correspond to any database object. Their meaning is entirely defined by your application. They're used to prevent duplicate cron job runs, protect critical business operations, and implement distributed mutexes.

Advisory lock patterns
-- Pattern: prevent duplicate cron job runs across multiple app servers
-- Use a consistent integer ID (e.g. hashtext of the job name)
DO $$
BEGIN
    IF pg_try_advisory_lock(hashtext('daily_report_job')) THEN
        -- only one server will enter here
        RAISE NOTICE 'Acquired lock, running job...';
        -- ... do the job ...
        PERFORM pg_advisory_unlock(hashtext('daily_report_job'));
    ELSE
        RAISE NOTICE 'Job already running on another server, skipping';
    END IF;
END;
$$;

Race Conditions — Real Problems and Correct Fixes

📖 35 min🐛 Production Critical

Race conditions only appear under concurrent load, pass all unit tests, and silently corrupt data. Every pattern here is a real class of production bug that affects experienced developers.

The Lost Update Problem

Three solutions, ranked by preference
-- THE BUG: two processes read stock=10, both subtract 1, both write 9
-- You sold 2 items but stock dropped by only 1

-- SOLUTION 1 (best): Atomic update -- let the database do the arithmetic
UPDATE products
SET stock_qty = stock_qty - 1
WHERE product_id = 1 AND stock_qty > 0;
-- Single statement = single lock. No race possible. Always use this for arithmetic.

-- SOLUTION 2: SELECT FOR UPDATE (pessimistic -- when you need to read first)
BEGIN;
SELECT stock_qty FROM products WHERE product_id = 1 FOR UPDATE;
-- validate business logic in application...
UPDATE products SET stock_qty = stock_qty - 1 WHERE product_id = 1;
COMMIT;

-- SOLUTION 3: Optimistic locking (high concurrency, infrequent conflicts)
ALTER TABLE products ADD COLUMN version INTEGER NOT NULL DEFAULT 1;
-- Read with version: stock_qty=10, version=5
UPDATE products
SET stock_qty = 9, version = version + 1
WHERE product_id = 1 AND version = 5; -- fails if another process already updated
-- Rows affected = 0: conflict, retry. = 1: success.

Double-Booking Prevention

Unique constraint is the correct tool
-- Check-then-insert is ALWAYS a race condition.
-- Two users check simultaneously, both see available, both insert.
CREATE TABLE bookings (
    room_id INTEGER, date DATE, user_id INTEGER,
    UNIQUE(room_id, date)  -- DB rejects the second booking automatically
);
INSERT INTO bookings(room_id, date, user_id) VALUES(42, '2025-12-25', 5)
ON CONFLICT(room_id, date) DO NOTHING RETURNING *;
-- Empty result = slot was already taken, show user an error message

Serializable Isolation for Complex Cases

When UNIQUE constraints are not enough
-- For complex business rules not expressible as a UNIQUE constraint,
-- SERIALIZABLE isolation detects any anomaly and aborts one transaction.
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT SUM(balance) FROM accounts WHERE user_id = 1;
-- check: total balance must stay above minimum...
UPDATE accounts SET balance = balance - 5000 WHERE account_id = 1;
COMMIT;
-- If a concurrent transaction creates a serialization anomaly:
-- ERROR: could not serialize access due to concurrent update
-- Application must catch this error code and retry the whole transaction

Write Skew — The Race Condition That REPEATABLE READ Doesn't Stop

Write skew is subtler than a lost update. Two transactions each read the same data, make a decision based on what they see, and write to different rows — but together their writes violate a business constraint. Neither transaction modified what the other read, so REPEATABLE READ cannot detect it. Only SERIALIZABLE isolation can.

Write skew — the hospital on-call scheduling example
-- RULE: at least one doctor must be on-call at all times
-- Dr. Priya reads: 2 doctors on-call. Decides it's safe to take the day off.
-- Dr. Rahul reads: 2 doctors on-call. Decides it's safe to take the day off.
-- Both commit. Now zero doctors on-call. Rule violated.
-- Neither overwrote the other's row — write skew, not a lost update.

-- WRONG: REPEATABLE READ does not protect against this
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT COUNT(*) FROM doctors WHERE on_call = true; -- sees 2
UPDATE doctors SET on_call = false WHERE doctor_id = 1;
COMMIT; -- succeeds even if concurrent session did the same for doctor_id = 2

-- CORRECT: SERIALIZABLE detects the anomaly and aborts one transaction
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT COUNT(*) FROM doctors WHERE on_call = true;
UPDATE doctors SET on_call = false WHERE doctor_id = 1;
COMMIT;
-- One of the two concurrent transactions gets:
-- ERROR:  could not serialize access due to concurrent update
-- That transaction must be retried. Second try: sees 1 on-call, might abort.

Phantom Reads — New Rows Appearing Between Reads

A phantom read occurs when a transaction reads a set of rows, another transaction inserts or deletes rows that match that same filter, and the first transaction's second read returns a different set. REPEATABLE READ prevents this in PostgreSQL (unlike SQL Server where it requires SERIALIZABLE).

Phantom read protection in PostgreSQL
-- Session A: count premium customers (REPEATABLE READ)
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT COUNT(*) FROM customers WHERE plan = 'premium'; -- returns 100

-- Session B (concurrent): inserts a new premium customer and commits
INSERT INTO customers(name, plan) VALUES('Arjun Sharma', 'premium'); COMMIT;

-- Session A: reads again in same transaction
SELECT COUNT(*) FROM customers WHERE plan = 'premium';
-- PostgreSQL REPEATABLE READ: still returns 100 (snapshot is fixed at BEGIN)
-- The new row is invisible -- no phantom read
-- SQL Server READ COMMITTED: would return 101 (sees new committed row)
-- This is a key difference from SQL Server behaviour you may be used to
COMMIT;

Exercise 6 — Running Total and % of Total Revenue Per Customer

Two window functions in the same query: a cumulative SUM for running total, and a ratio over the whole partition for contribution. This is the "running total leaderboard" query every analyst needs.

SUM() OVER() and ratio to total
WITH customer_rev AS (
    SELECT
        c.customer_id,
        c.first_name || ' ' || c.last_name   AS customer,
        SUM(o.total_amount)                   AS revenue
    FROM customers c
    JOIN orders o ON c.customer_id = o.customer_id

    customer,
    revenue,

FROM customer_rev

Exercise 7 — Day-7 Retention Rate

For each week, what percentage of new customers placed a second order within 7 days? This pattern appears in almost every analytics interview and every product dashboard.

Cohort retention with date arithmetic
WITH first_orders AS (
    SELECT
        customer_id,
        MIN(order_date)                        AS first_order_date,
        DATE_TRUNC('week', MIN(order_date))   AS cohort_week
    FROM orders
    GROUP BY customer_id
),
retained AS (
    SELECT f.cohort_week, f.customer_id
    FROM first_orders f
    WHERE EXISTS (
        SELECT 1 FROM orders o
        WHERE o.customer_id = f.customer_id
          AND o.order_date > f.first_order_date
          AND o.order_date <= f.first_order_date + INTERVAL '7 days'
    )
)
SELECT
    f.cohort_week::date,
    COUNT(DISTINCT f.customer_id)           AS new_customers,
    COUNT(DISTINCT r.customer_id)           AS retained_day7,
    ROUND(COUNT(DISTINCT r.customer_id) * 100.0
        / COUNT(DISTINCT f.customer_id), 1) AS day7_retention_pct
FROM first_orders f
LEFT JOIN retained r ON r.cohort_week = f.cohort_week
                    AND r.customer_id = f.customer_id
GROUP BY f.cohort_week
ORDER BY f.cohort_week;

Incident 1: ALTER TABLE Locking at Peak Hours

The incident and the zero-downtime fix

-- Step 1: Add nullable column (instant in PG11+)
ALTER TABLE orders ADD COLUMN notes TEXT;
-- Step 2: Backfill in batches (no long lock held)
UPDATE orders SET notes = '' WHERE notes IS NULL AND order_id BETWEEN 1 AND 100000;
-- ...repeat for each 100k batch...
-- Step 3: Add constraint without scanning (NOT VALID)
ALTER TABLE orders ADD CONSTRAINT chk_notes CHECK(notes IS NOT NULL) NOT VALID;
-- Later: validate in background (doesn't block reads)
ALTER TABLE orders VALIDATE CONSTRAINT chk_notes;

Query & Performance Tuning — Complete Playbook

Step 1 — Find Slow Queries in Production with pg_stat_statements

You cannot tune what you cannot measure. pg_stat_statements tracks every distinct query pattern across all sessions, accumulating total time, call count, I/O, and variance. It is the single most important tool for production performance work.

Enable and query pg_stat_statements
-- Enable on Cloud SQL (flag, requires restart)
-- gcloud sql instances patch INSTANCE --database-flags pg_stat_statements.track=all

-- Activate extension in your database
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- TOP 10 queries by total time consumed (most impactful to optimize)
SELECT
    ROUND(total_exec_time / 1000, 2)                     AS total_sec,
    calls,
    ROUND(mean_exec_time, 2)                              AS mean_ms,
    ROUND(stddev_exec_time, 2)                            AS stddev_ms,
    ROUND(rows / calls::numeric, 1)                       AS avg_rows,
    ROUND((shared_blks_hit + shared_blks_read)::numeric
           / calls, 1)                                    AS blks_per_call,
    LEFT(query, 120)                                       AS query_sample
FROM pg_stat_statements
WHERE calls > 100
ORDER BY total_exec_time DESC
LIMIT 10;

-- TOP 10 by mean execution time (single worst queries)
SELECT
    ROUND(mean_exec_time, 2)   AS mean_ms,
    calls,
    LEFT(query, 120)           AS query_sample
FROM pg_stat_statements
WHERE calls > 10
ORDER BY mean_exec_time DESC
LIMIT 10;

-- TOP 10 by I/O (most disk reads — index missing or data not in cache)
SELECT
    calls,
    ROUND(shared_blks_read::numeric / calls, 1)   AS disk_reads_per_call,
    ROUND(shared_blks_hit::numeric /
        NULLIF(shared_blks_hit + shared_blks_read, 0) * 100, 1) AS cache_hit_pct,
    LEFT(query, 120)             AS query_sample
FROM pg_stat_statements
WHERE shared_blks_read > 0 AND calls > 10
ORDER BY shared_blks_read / calls DESC
LIMIT 10;

-- Reset statistics (do this periodically or after a tuning change)
SELECT pg_stat_statements_reset();

    indexrelname,
    pg_size_pretty(pg_relation_size(indexrelid)) AS index_size,
    idx_scan, idx_tup_read, idx_tup_fetch,
    ROUND(idx_tup_read::numeric / NULLIF(idx_scan, 0), 0) AS avg_rows_per_scan
FROM pg_stat_user_indexes
JOIN pg_index ON pg_index.indexrelid = pg_stat_user_indexes.indexrelid
WHERE NOT pg_index.indisvalid  -- invalid indexes = REINDEX needed
ORDER BY pg_relation_size(indexrelid) DESC;

-- Rebuild a bloated index without locking the table
REINDEX INDEX CONCURRENTLY idx_orders_customer_date;

Step 5 — Query Rewrite Patterns

Many slow queries can be fixed without adding indexes — just by writing the SQL differently. These 8 patterns cover the most common rewrites.

Pattern 1: Function on indexed column defeats the index
-- ❌ SLOW: LOWER() wrapping prevents index use on email
SELECT * FROM customers WHERE LOWER(email) = 'priya@example.com';

-- ✅ FIX A: store data lowercase (enforce at insert time)
ALTER TABLE customers ADD CONSTRAINT email_lower
    CHECK (email = LOWER(email));

-- ✅ FIX B: expression index on LOWER(email)
CREATE INDEX idx_customers_email_lower ON customers (LOWER(email));
-- Same issue with: DATE(timestamp_col), CAST(col AS type), any function wrap
Pattern 2: Implicit type cast defeats index
-- Column is INTEGER, but parameter sent as TEXT string — implicit cast applied
-- ❌ SLOW: planner may not use the index due to type mismatch
SELECT * FROM orders WHERE customer_id = '42';

-- ✅ FAST: match parameter type to column type
SELECT * FROM orders WHERE customer_id = 42;

-- Common in ORMs sending everything as VARCHAR — check pg_stat_statements
-- for queries with "::text" or "::integer" casts appearing in the query text
Pattern 3: NOT IN with NULLs returns empty result
-- ❌ WRONG AND SLOW: if any order has customer_id = NULL, returns nothing
-- NULL comparisons with IN/NOT IN follow 3-valued logic
SELECT * FROM customers
WHERE customer_id NOT IN (SELECT customer_id FROM orders);

-- ✅ CORRECT AND FAST: NOT EXISTS handles NULLs correctly + uses index
SELECT * FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
);
Pattern 4: DISTINCT to hide a join problem
-- ❌ SLOW: DISTINCT added to suppress duplicates from a bad join
-- The sort + dedup makes this O(n log n) on the full result
SELECT DISTINCT c.customer_id, c.email
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id;

-- ✅ FAST: use EXISTS — stops at the first matching row
SELECT c.customer_id, c.email
FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
Patterns 5-8: LIKE wildcards, OR rewrite, N+1, pagination
-- Pattern 5: Leading wildcard disables B-tree (use pg_trgm GIN for contains search)
-- ❌ SLOW: leading % = full index scan
SELECT * FROM products WHERE name LIKE '%phone%';
-- ✅ FAST: trigram index supports contains search
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_products_name_trgm ON products USING GIN (name gin_trgm_ops);
SELECT * FROM products WHERE name ILIKE '%phone%'; -- now uses index

-- Pattern 6: UNION ALL instead of OR for multi-column index use
-- ❌ SLOW: OR on different columns prevents index-only scans
SELECT * FROM customers WHERE email = 'a@b.com' OR phone = '9848012345';
-- ✅ FAST: each branch uses its own index
SELECT * FROM customers WHERE email = 'a@b.com'
UNION ALL
SELECT * FROM customers WHERE phone = '9848012345' AND email != 'a@b.com';

-- Pattern 7: N+1 — never loop and query, batch instead
-- ❌ SLOW: 1000 orders = 1000 separate customer queries from app code
-- for order in orders: db.query("SELECT * FROM customers WHERE id = %s", order.customer_id)
-- ✅ FAST: single JOIN fetches everything
SELECT o.order_id, o.total_amount, c.email, c.first_name
FROM orders o JOIN customers c ON c.customer_id = o.customer_id
WHERE o.order_id = ANY(ARRAY[1,2,3,...]);

-- Pattern 8: Keyset pagination vs OFFSET (OFFSET scans and discards all preceding rows)
-- ❌ SLOW at page 500: scans 5000 rows to discard them
SELECT * FROM orders ORDER BY order_id LIMIT 10 OFFSET 5000;
-- ✅ FAST: keyset pagination — resume from last seen ID
SELECT * FROM orders
WHERE order_id > 5000   -- last order_id from previous page
ORDER BY order_id LIMIT 10; -- instant at any depth

Step 6 — Buffer Cache and Memory Tuning

The fastest query is one that reads from RAM. PostgreSQL has a shared buffer cache (shared_buffers) — all instances share it. A cache hit ratio below 95% on an OLTP workload means either the working set is larger than memory, or shared_buffers is too small.

Cache hit ratio and buffer diagnostics
-- Overall database cache hit ratio (should be > 95% for OLTP)
SELECT
    SUM(heap_blks_hit)   AS cache_hits,
    SUM(heap_blks_read)  AS disk_reads,
    ROUND(SUM(heap_blks_hit) * 100.0
        / NULLIF(SUM(heap_blks_hit) + SUM(heap_blks_read), 0), 2) AS cache_hit_pct
FROM pg_statio_user_tables;

-- Per-table cache hit ratio (find which tables are missing cache)
SELECT
    relname,
    heap_blks_hit,
    heap_blks_read,
    ROUND(heap_blks_hit * 100.0
        / NULLIF(heap_blks_hit + heap_blks_read, 0), 2) AS hit_pct
FROM pg_statio_user_tables
WHERE heap_blks_read > 0
ORDER BY heap_blks_read DESC LIMIT 10;
-- Tables with low hit_pct = frequently read but not in cache
-- Solution: increase shared_buffers, or use pg_prewarm to pre-load hot tables

-- Pre-warm a table into shared_buffers after a restart
CREATE EXTENSION IF NOT EXISTS pg_prewarm;
SELECT pg_prewarm('orders', 'buffer');
SELECT pg_prewarm('idx_orders_customer_date', 'buffer');

Streaming Replication — How It Works

The primary continuously streams WAL records to one or more standbys. Each standby has a WAL receiver process that applies the records, keeping the standby within milliseconds of the primary. The standby can serve read-only queries while in recovery mode.

Monitor streaming replication health (run on primary)
-- Is streaming replication connected and what is the lag?
SELECT
    client_addr                                    AS standby_ip,
    state,                                         -- streaming = healthy
    sync_state,                                    -- async/sync/quorum
    sent_lsn,
    write_lsn,
    flush_lsn,
    replay_lsn,
    pg_size_pretty(
        pg_wal_lsn_diff(sent_lsn, replay_lsn))    AS replication_lag_bytes,
    replay_lag                                     AS replication_lag_time
FROM pg_stat_replication
ORDER BY replay_lag DESC NULLS LAST;
-- state = 'streaming': connected and receiving WAL ✅
-- state = 'catchup':   standby is behind, catching up
-- state = null:        standby disconnected ❌
-- replay_lag > 30s:    investigate ⚠️

-- On the STANDBY: verify it is in recovery and not lagging

    pg_is_in_recovery()           AS is_standby,
    pg_last_wal_receive_lsn()     AS received_up_to,
    pg_last_wal_replay_lsn()      AS applied_up_to,
    pg_last_xact_replay_timestamp() AS last_transaction_replayed,
    NOW() - pg_last_xact_replay_timestamp() AS lag;

Roles, Privileges & Security

📖 45 min🔒 Access Control

In PostgreSQL, users and groups are both called roles. A role with LOGIN is a user. A role without LOGIN is a group. Privileges are granted to roles, roles are granted to other roles, and users inherit permissions from every role they belong to. Getting this right is fundamental to running a multi-team or multi-application database safely.

Role Hierarchy — The Right Way to Structure Access

Create a clean role hierarchy for a production database
-- ── ROLE HIERARCHY PATTERN ──────────────────────────────────────
-- app_readonly     → SELECT only (analytics, reporting tools)
-- app_readwrite    → SELECT, INSERT, UPDATE, DELETE (application)
-- app_admin        → full table ownership (DBA, migrations)
-- replicator       → REPLICATION only (streaming + logical replication)
-- ──────────────────────────────────────────────────────────────────

-- Step 1: Create group roles (no LOGIN — they are permission bundles)
CREATE ROLE app_readonly;
CREATE ROLE app_readwrite;
CREATE ROLE app_admin;

-- Step 2: Grant schema access to all roles
GRANT USAGE ON SCHEMA public TO app_readonly, app_readwrite, app_admin;

-- Step 3: Grant table privileges to group roles
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_readonly;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO app_readwrite;
GRANT ALL ON ALL TABLES IN SCHEMA public TO app_admin;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_readwrite, app_admin;

-- Step 4: Auto-grant for FUTURE tables (critical — often forgotten)
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT ON TABLES TO app_readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_readwrite;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT USAGE, SELECT ON SEQUENCES TO app_readwrite, app_admin;

-- Step 5: Create actual user accounts and assign roles
CREATE ROLE api_service WITH LOGIN PASSWORD 'StrongPass123!' CONNECTION LIMIT 20;
GRANT app_readwrite TO api_service;

CREATE ROLE analytics_user WITH LOGIN PASSWORD 'StrongPass456!' CONNECTION LIMIT 5;
GRANT app_readonly TO analytics_user;

CREATE ROLE dba_priya WITH LOGIN PASSWORD 'StrongPass789!' SUPERUSER;
-- SUPERUSER bypasses all privilege checks — use sparingly, audit carefully

Connection Management

📖 35 min🔌 Infrastructure

PostgreSQL spawns a separate OS process for every connection. At 200 connections you have 200 processes competing for CPU and RAM. At 500 connections you are burning memory on idle processes and context switching becomes a measurable overhead. Connection management is one of the most common production failure modes.

What Happens When You Hit max_connections

Connection monitoring — run this as a daily alert query
-- Current connection usage vs limit
SELECT
    COUNT(*)                               AS total_connections,
    COUNT(*) FILTER(WHERE state = 'active')    AS active,
    COUNT(*) FILTER(WHERE state = 'idle')      AS idle,
    COUNT(*) FILTER(WHERE state = 'idle in transaction') AS idle_in_txn,
    (SELECT setting::int FROM pg_settings WHERE name = 'max_connections') AS max_connections,
    ROUND(COUNT(*) * 100.0 /
        (SELECT setting::int FROM pg_settings WHERE name = 'max_connections'), 1) AS pct_used
FROM pg_stat_activity;
-- Alert when pct_used > 80%
-- idle_in_txn > 10: serious problem — connection leak or stuck transaction
-- When max_connections is reached: new connections get
-- "FATAL: remaining connection slots are reserved for non-replication superuser connections"

-- Find long-running idle-in-transaction connections (connection leak)
SELECT
    pid, usename, application_name, client_addr,
    state,
    NOW() - state_change   AS time_in_state,
    LEFT(query, 100)       AS last_query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND NOW() - state_change > INTERVAL '5 minutes'
ORDER BY time_in_state DESC;

-- Kill a specific connection (last resort)
SELECT pg_terminate_backend(12345);  -- graceful: rolls back transaction
SELECT pg_cancel_backend(12345);    -- cancel current query, keep connection

-- Kill all idle-in-transaction older than 10 minutes (batch cleanup)
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND NOW() - state_change > INTERVAL '10 minutes';

VACUUM at Scale

📖 45 min🧹 Operational Mastery

VACUUM is PostgreSQL's housekeeping process. On a lightly used database it runs quietly in the background and you never think about it. On a high-write production database — millions of updates per day — VACUUM tuning is the difference between a healthy database and one that bloats, slows down, and eventually stops accepting writes due to transaction ID wraparound.

The Three Jobs of VACUUM

JobWhat it doesWithout it
Dead tuple reclamationMarks space from deleted/updated rows as reusableTable grows indefinitely (bloat). Seq scans read dead rows.
Visibility map updateMarks pages that contain only live rows (enables Index-Only Scans)Index-Only Scans degrade into heap fetches. Query performance drops.
Transaction ID freezeReplaces old xmin values with "frozen" marker to prevent wraparoundDatabase shuts down writes at 2.1B transactions. Requires emergency VACUUM FREEZE.

Autovacuum Default Behavior — Why It Fails on Busy Tables

Autovacuum triggers when dead tuples exceed autovacuum_vacuum_scale_factor × reltuples + autovacuum_vacuum_threshold. The default scale factor is 20%. On a 50M row table, autovacuum does not trigger until 10M dead tuples accumulate — by which point the table has significant bloat and the VACUUM run itself takes hours.

Identify tables where autovacuum is falling behind
-- Tables most in need of VACUUM attention

    schemaname,
    relname                                                    AS table_name,
    n_live_tup,
    n_dead_tup,

    n_mod_since_analyze,
    last_vacuum::date,
    last_autovacuum::date,
    last_analyze::date,
    autovacuum_count,
    age(relfrozenxid)                                         AS xid_age
FROM pg_stat_user_tables t
JOIN pg_class c ON c.relname = t.relname
WHERE t.schemaname = 'public'
ORDER BY n_dead_tup DESC
LIMIT 20;

-- last_autovacuum = NULL or many days ago: autovacuum not keeping up

VACUUM FREEZE orders;              -- force-freeze all rows (high I/O — off peak)

Bloat Emergency — When VACUUM Is Not Enough

Regular VACUUM marks dead space as reusable but does not return it to the OS. A table that was once 100GB and is now logically 20GB still occupies 100GB on disk. The only ways to reclaim that space are VACUUM FULL (which rewrites the entire table with an ACCESS EXCLUSIVE lock) or pg_repack (which does the same thing online without a lock).

Bloat recovery options
-- Option 1: VACUUM FULL — rewrites table, reclaims disk, ACCESS EXCLUSIVE lock
-- Duration: minutes to hours depending on table size
-- Impact: ALL reads and writes blocked during rewrite
VACUUM FULL VERBOSE orders;

-- Option 2: pg_repack — online table rewrite, no long lock (preferred for production)
-- Install: CREATE EXTENSION pg_repack;
-- Runs as: pg_repack -h HOST -d DB -t orders
-- Works by: building new table in background, swapping with minimal lock at end
-- Duration: similar to VACUUM FULL but without downtime
CREATE EXTENSION IF NOT EXISTS pg_repack;

    pg_size_pretty(pg_relation_size(oid))           AS table_size,
    pg_size_pretty(pg_indexes_size(oid))            AS indexes_size
FROM pg_class
WHERE relname = 'orders';

Capacity planning means answering the question: how long until we run out of connections, disk, transaction IDs, or CPU? The DBA who can answer this in a weekly review prevents outages. The DBA who cannot answer it gets paged at 2am.

Measure current database size and top tables

Transaction ID Exhaustion Projection

Monitor and project XID wraparound timeline
-- Current XID age and estimated time remaining
WITH xid_stats AS (
    SELECT
        MAX(age(relfrozenxid))      AS max_age,
        2100000000                  AS danger_threshold
    FROM pg_class
    WHERE relkind = 'r'
)
SELECT
    max_age                                                        AS current_xid_age,
    danger_threshold - max_age                                     AS xids_remaining,
    ROUND((danger_threshold - max_age)::numeric / danger_threshold * 100, 1) AS pct_safe,
    CASE
        WHEN max_age > 1500000000 THEN '🔴 EMERGENCY — VACUUM FREEZE IMMEDIATELY'
        WHEN max_age > 1000000000 THEN '🟠 WARNING — Schedule VACUUM FREEZE this week'
        WHEN max_age > 500000000  THEN '🟡 WATCH — Monitor weekly'
        ELSE                            '🟢 OK'
    END AS status
FROM xid_stats;

-- Which tables are oldest? (freeze these first)
SELECT relname, age(relfrozenxid) AS xid_age,
    pg_size_pretty(pg_total_relation_size(oid)) AS size
FROM pg_class
WHERE relkind = 'r' AND age(relfrozenxid) > 200000000
ORDER BY xid_age DESC LIMIT 10;

Zero-Downtime Migration via Logical Replication

This is the safest approach for any migration requiring near-zero downtime. You run the old and new system in parallel, use logical replication to keep them in sync, then cut over with a 5-30 second maintenance window for the final WAL drain.

The 7-step logical replication migration playbook
-- STEP 1: New instance ready (new version, new Cloud SQL tier, etc.)
-- STEP 2: Set up logical replication from OLD → NEW (Module 7 procedure)
--         CREATE PUBLICATION on old, CREATE SUBSCRIPTION on new
-- STEP 3: Wait for initial sync to complete (all tables in 'r' state)
SELECT relid::regclass, srsubstate
FROM pg_subscription_rel;       -- all should be 'r' before proceeding

-- STEP 4: Monitor replication lag — wait until near-zero
SELECT subname, received_lsn, latest_end_lsn,
    NOW() - last_msg_receipt_time AS message_lag
FROM pg_stat_subscription;      -- message_lag should be < 1 second

-- STEP 5: Maintenance window start (brief — 5-30 seconds)
--   a) Put application into maintenance mode (return 503, queue requests)
--   b) Wait for replication lag to reach zero
--   c) On OLD: verify no active transactions
SELECT COUNT(*) FROM pg_stat_activity
WHERE state != 'idle' AND pid != pg_backend_pid();

-- STEP 6: Switch application connection strings to NEW database
-- STEP 7: Verify application is healthy on NEW, then drop subscription and old instance
DROP SUBSCRIPTION sub_migration;     -- run on new instance
-- DROP PUBLICATION pub_migration;   -- run on old instance
-- Delete or archive old instance after 48 hours (safety window)

Pre-Upgrade Compatibility Checklist

Run these checks before any major upgrade
-- 1. Check for deprecated functions and syntax in your queries
-- PG17 removals: query_to_xml, some GUC changes — check release notes
-- https://www.postgresql.org/docs/17/release-17.html (search "Incompatibilities")

-- 2. Check extensions and their compatibility
SELECT name, installed_version FROM pg_available_extensions
WHERE installed_version IS NOT NULL;

-- 3. Check for tables using deprecated storage types (rare but exists)
SELECT relname, relam FROM pg_class
WHERE relkind = 'r' AND relam != (SELECT oid FROM pg_am WHERE amname = 'heap');

-- 4. Verify foreign key referential integrity (upgrade fails if violated)
-- pg_dump --schema-only to test restore on target version

-- 5. Take baseline performance metrics (pg_stat_statements, table sizes)
-- Compare these metrics after upgrade — query plans may change after ANALYZE

-- 6. Test application against the upgraded clone
-- Run: SELECT version(); after upgrade to confirm new version active
SELECT version();
SELECT current_setting('server_version_num');  -- e.g. 170007 for PG17.7
⚠️

The most common upgrade mistake

Upgrading production directly without testing on a clone first. A clone upgrade that fails costs nothing. A production upgrade that fails at 11pm costs hours of downtime and a reputation. Always: clone → upgrade clone → run test suite → fix issues → upgrade production. Never skip this on a database with production traffic.
