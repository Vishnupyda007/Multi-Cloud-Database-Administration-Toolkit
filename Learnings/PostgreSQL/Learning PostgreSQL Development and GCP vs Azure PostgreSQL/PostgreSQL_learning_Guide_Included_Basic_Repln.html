What is PostgreSQL?

📖 10 min read 🎯 Foundation

PostgreSQL (pronounced post-gress-Q-L, often called Postgres) is a powerful, open-source relational database system with over 35 years of active development. It is trusted by companies like Apple, Instagram, Spotify, Reddit, and countless others.

Why PostgreSQL?

🆓

Free & Open Source

No licensing costs. Backed by a vibrant global community since 1986.

🔒

ACID Compliant

Rock-solid transactions — Atomicity, Consistency, Isolation, Durability guaranteed.

🧩

Extensible

Custom data types, functions, operators, and extensions like PostGIS, pgvector.

📊

SQL Standard

Most SQL-standard compliant RDBMS available. Your SQL skills transfer directly.

🌐

JSON & NoSQL

Full JSONB support means relational + document storage in one database.

⚡

High Performance

Parallel queries, advanced indexing (B-tree, GIN, GiST, BRIN), partitioning.

The PostgreSQL Architecture

Understanding the architecture helps you manage and troubleshoot your database. Here's the hierarchy:

1

PostgreSQL Server (Instance)

The running database server process. One server can host many databases.

2

Database

An isolated container. Each database has its own users, schemas, and tables. (e.g., myapp_db)

3

Schema

A namespace inside a database. The default schema is public. You can create schemas like sales, hr.

4

Table

Where data lives — rows and columns. Belongs to a schema. Full name: schema.table → public.orders

5

Row (Tuple)

A single record in a table. PostgreSQL calls rows "tuples" internally.

The CREATE TABLE statement defines the structure of your data. Each column has a name and a data type.

Create customers table
CREATE TABLE customers (
    customer_id   SERIAL        PRIMARY KEY,
    first_name    VARCHAR(100)  NOT NULL,
    last_name     VARCHAR(100)  NOT NULL,

    created_at    TIMESTAMP     DEFAULT NOW()
);
Create products table
CREATE TABLE products (
    product_id    SERIAL          PRIMARY KEY,
    name          VARCHAR(200)    NOT NULL,
    category      VARCHAR(100),
    price         NUMERIC(10,2)   NOT NULL,

    is_active     BOOLEAN         DEFAULT TRUE,
    created_at    TIMESTAMP       DEFAULT NOW()
);
Create orders table
CREATE TABLE orders (
    order_id      SERIAL          PRIMARY KEY,
    customer_id   INTEGER         NOT NULL REFERENCES customers(customer_id),
    order_date    TIMESTAMP       DEFAULT NOW(),
    total_amount  NUMERIC(12,2)   NOT NULL DEFAULT 0,
    status        VARCHAR(50)     DEFAULT 'pending',
    notes         TEXT
);

Quick Check: What does SERIAL do in PostgreSQL?

✅ Correct! SERIAL is shorthand for an integer column backed by a sequence — equivalent to IDENTITY(1,1) in SQL Server. Each new row gets the next number automatically.
❌ Not quite. SERIAL creates an auto-incrementing integer — like IDENTITY(1,1) in SQL Server. Each INSERT gets the next number automatically.

INSERT with RETURNING

This is a powerful PostgreSQL feature with no SQL Server equivalent. You can get back the inserted row's data immediately — very useful for getting auto-generated IDs.

INSERT ... RETURNING
-- Get the new customer_id right after inserting
INSERT INTO customers (first_name, last_name, email)
VALUES ('Vikram', 'Singh', 'vikram@example.com')
RETURNING customer_id, created_at;

-- Returns:
-- customer_id |        created_at
-- ────────────+──────────────────────────
--           6 | 2025-06-18 10:30:00.123

UPSERT — INSERT or UPDATE (ON CONFLICT)

Upsert is the pattern "insert if not exists, update if it does." PostgreSQL's syntax is elegant.

ON CONFLICT (Upsert)
-- Insert, or update price/stock if product name already exists
INSERT INTO products (name, category, price, stock_qty)
VALUES ('Wireless Mouse', 'Electronics', 1199.00, 200)
ON CONFLICT (name)
DO UPDATE SET
    price     = EXCLUDED.price,
    stock_qty = EXCLUDED.stock_qty;

-- EXCLUDED refers to the row that WOULD have been inserted

-- Or: do nothing on conflict
INSERT INTO customers (email, first_name, last_name)
VALUES ('priya@example.com', 'Priya', 'S')
ON CONFLICT (email) DO NOTHING;
🔄

SQL Server MERGE vs PostgreSQL ON CONFLICT

SQL Server uses MERGE for upsert operations. PostgreSQL's INSERT ... ON CONFLICT is simpler and safer. PostgreSQL 15+ also has a MERGE statement if you prefer that syntax.

Filtering with WHERE

WHERE clause
-- Exact match
SELECT * FROM customers WHERE city = 'Hyderabad';

-- Numeric comparisons
SELECT name, price FROM products WHERE price > 5000;

  AND is_active = TRUE;

ORDER BY

-- Sort descending
SELECT name, price FROM products ORDER BY price DESC;

-- Sort by multiple columns
SELECT * FROM products
ORDER BY category ASC, price DESC;

-- NULLs go last (default is NULLS LAST in PostgreSQL for DESC)
SELECT * FROM customers

UPDATE & DELETE

📖 15 min🛠 Hands-on

UPDATE — Modifying Existing Data

UPDATE examples
-- Update a single row
UPDATE customers
SET city = 'Hyderabad', phone = '+91 98765 43210'
WHERE customer_id = 1;

-- Update multiple rows matching a condition
UPDATE products
SET is_active = FALSE
WHERE stock_qty = 0;

-- Update using a calculation
UPDATE products
SET price = price * 1.10  -- 10% price increase
WHERE category = 'Electronics';

-- UPDATE with RETURNING (see what changed)
UPDATE products
SET stock_qty = stock_qty + 50
WHERE name = 'Coffee Maker'
RETURNING name, stock_qty;
⚠️

Always Use WHERE with UPDATE

An UPDATE without a WHERE clause updates EVERY row in the table. Always add a WHERE condition. Best practice: run the equivalent SELECT first to verify which rows you'll affect, then change SELECT to UPDATE.

DELETE — Removing Rows

DELETE examples
-- Delete a specific row
DELETE FROM customers WHERE customer_id = 5;

-- Delete rows matching a condition
DELETE FROM products
WHERE is_active = FALSE AND stock_qty = 0;

-- Delete with RETURNING (confirm what was deleted)
DELETE FROM orders
WHERE status = 'cancelled'
  AND order_date < NOW() - INTERVAL '1 year'
RETURNING order_id, order_date;

TRUNCATE — Fast Table Clear

TRUNCATE
-- Remove ALL rows from a table (much faster than DELETE)
TRUNCATE TABLE orders;

-- Also reset the sequence (auto-increment back to 1)
TRUNCATE TABLE orders RESTART IDENTITY;

-- Truncate multiple tables
TRUNCATE TABLE orders, customers CASCADE;
🔄

SQL Server vs PostgreSQL DELETE/TRUNCATE

PostgreSQL's TRUNCATE is transactional (can be rolled back!) unlike SQL Server. Also, PostgreSQL has no DELETE TOP(n) syntax — use a subquery or CTE with LIMIT instead.

Filtering & Sorting — Deep Dive

📖 20 min🛠 Hands-on

Advanced WHERE Conditions

Advanced filtering
-- CASE WHEN in SELECT (conditional logic)
SELECT
    name,
    price,
    CASE
        WHEN price < 1000  THEN 'Budget'
        WHEN price < 10000 THEN 'Mid-range'
        ELSE 'Premium'
    END AS price_tier
FROM products;

-- Subquery in WHERE
SELECT * FROM customers
WHERE customer_id IN (
    SELECT DISTINCT customer_id FROM orders
    WHERE total_amount > 50000
);

-- EXISTS subquery (often faster than IN for large sets)
SELECT * FROM customers c
WHERE EXISTS (
    SELECT 1 FROM orders o
    WHERE o.customer_id = c.customer_id
      AND o.status = 'delivered'
);

Date Filtering

Date queries
-- Orders from today
SELECT * FROM orders
WHERE order_date::date = CURRENT_DATE;

-- Orders in last 30 days
SELECT * FROM orders
WHERE order_date >= NOW() - INTERVAL '30 days';

-- Orders in a specific month
SELECT * FROM orders
WHERE DATE_TRUNC('month', order_date) = '2025-01-01';

-- Extract parts of a date
SELECT
    order_id,
    EXTRACT(YEAR  FROM order_date) AS order_year,
    EXTRACT(MONTH FROM order_date) AS order_month,
    EXTRACT(DOW   FROM order_date) AS day_of_week  -- 0=Sun, 6=Sat
FROM orders;

COALESCE — Handle NULLs

COALESCE & NULLIF
-- COALESCE returns the first non-NULL value (like ISNULL in SQL Server)
SELECT
    first_name,
    COALESCE(phone, 'No phone')     AS phone,
    COALESCE(city, country, 'Unknown') AS location
FROM customers;

-- NULLIF returns NULL if two values are equal (avoids division by zero)
SELECT
    total_amount / NULLIF(quantity, 0) AS unit_price
FROM orders;

Joins — Combining Tables

📖 30 min🛠 Core Skill

Joins are how you combine data from multiple tables. This is where relational databases shine.

INNER JOIN — Only Matching Rows

INNER JOIN
-- Get orders WITH customer names (only customers who have orders)
SELECT
    o.order_id,
    o.order_date,
    o.total_amount,
    o.status,
    c.first_name || ' ' || c.last_name AS customer_name,
    c.email
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id
ORDER BY o.order_date DESC;

LEFT JOIN — All from Left Table

LEFT JOIN
-- ALL customers, with their orders (NULL if no orders)
SELECT
    c.customer_id,
    c.first_name,
    c.last_name,
    COUNT(o.order_id)           AS order_count,
    COALESCE(SUM(o.total_amount), 0) AS total_spent
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.first_name, c.last_name
ORDER BY total_spent DESC;

-- Find customers with NO orders
SELECT c.* FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL;

Joining 3 Tables

3-table join
-- Create order_items table first
CREATE TABLE order_items (
    item_id    SERIAL   PRIMARY KEY,
    order_id   INTEGER  NOT NULL REFERENCES orders(order_id),
    product_id INTEGER  NOT NULL REFERENCES products(product_id),
    quantity   INTEGER  NOT NULL DEFAULT 1,
    unit_price NUMERIC(10,2)
);

-- Join customers → orders → order_items → products
SELECT
    c.first_name || ' ' || c.last_name AS customer,
    o.order_id,
    p.name                              AS product,
    oi.quantity,
    oi.unit_price,
    oi.quantity * oi.unit_price         AS line_total
FROM customers   c
JOIN orders      o  ON c.customer_id = o.customer_id
JOIN order_items oi ON o.order_id   = oi.order_id
JOIN products    p  ON oi.product_id = p.product_id
ORDER BY o.order_id, p.name;

Aggregations — GROUP BY & Analytics

📖 25 min🛠 Hands-on

Aggregate Functions

Core aggregates
-- Summary statistics on products
SELECT
    COUNT(*)                    AS total_products,
    COUNT(DISTINCT category)   AS unique_categories,
    MIN(price)                  AS cheapest,
    MAX(price)                  AS most_expensive,
    AVG(price)::NUMERIC(10,2)   AS avg_price,
    SUM(stock_qty)             AS total_stock
FROM products;

GROUP BY — Aggregate by Category

GROUP BY
-- Sales by product category
SELECT
    p.category,
    COUNT(oi.item_id)            AS items_sold,
    SUM(oi.quantity)             AS total_qty,
    SUM(oi.quantity * oi.unit_price) AS revenue,
    AVG(p.price)::NUMERIC(10,2)  AS avg_price
FROM products    p
JOIN order_items oi ON p.product_id = oi.product_id
GROUP BY p.category
ORDER BY revenue DESC;

HAVING — Filter on Aggregated Results

HAVING
-- WHERE filters BEFORE grouping, HAVING filters AFTER

-- Only categories with more than 5 products
SELECT category, COUNT(*) AS product_count
FROM products
WHERE is_active = TRUE           -- applied before grouping
GROUP BY category
HAVING COUNT(*) > 5             -- applied after grouping
ORDER BY product_count DESC;

-- Top customers who spent over ₹1,00,000
SELECT
    c.first_name || ' ' || c.last_name AS customer,
    SUM(o.total_amount) AS total_spent
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.first_name, c.last_name
HAVING SUM(o.total_amount) > 100000
ORDER BY total_spent DESC;

📋

The ORDER SQL Executes (not how you write it)

1. FROM + JOIN — get the data sources    2. WHERE — filter rows    3. GROUP BY — group remaining rows    4. HAVING — filter groups    5. SELECT — pick columns    6. ORDER BY — sort    7. LIMIT/OFFSET — paginate

Indexes — Supercharge Query Speed

📖 20 min⚡ Performance

An index is like a book's table of contents — it lets PostgreSQL find rows without reading every single row in the table.

Creating Indexes

Index creation
-- Basic B-tree index (default, most common)
CREATE INDEX idx_customers_email
    ON customers(email);

-- Composite index (multiple columns)
CREATE INDEX idx_orders_customer_date
    ON orders(customer_id, order_date);

-- Unique index (ensures no duplicates + index)
CREATE UNIQUE INDEX idx_products_name
    ON products(name);

-- Partial index (only index rows matching a condition)
-- Much smaller + faster for common filtered queries
CREATE INDEX idx_active_products
    ON products(category, price)
    WHERE is_active = TRUE;

-- Create index CONCURRENTLY (no table lock — use on production!)
CREATE INDEX CONCURRENTLY idx_orders_status
    ON orders(status);

-- Drop an index
DROP INDEX idx_customers_email;

Golden Rules for Indexes

Transactions — ACID Guarantees

📖 20 min🔒 Critical

A transaction groups multiple SQL statements so they succeed or fail together. This is the foundation of data integrity.

Basic Transaction Syntax

Transaction example
-- Transfer money between accounts (classic example)
BEGIN;    -- Start transaction

    UPDATE accounts
    SET balance = balance - 5000
    WHERE account_id = 101;   -- deduct from sender

    UPDATE accounts
    SET balance = balance + 5000
    WHERE account_id = 202;   -- add to receiver

    INSERT INTO transfer_log (from_id, to_id, amount)
    VALUES (101, 202, 5000);

COMMIT;   -- All three statements succeed together

-- If anything fails, use ROLLBACK to undo everything:
BEGIN;
    UPDATE ...;
    -- Error occurs here
ROLLBACK;  -- Undo all changes in this transaction

SAVEPOINT — Partial Rollback

SAVEPOINT
BEGIN;

    INSERT INTO orders (...) VALUES (...);

    SAVEPOINT after_order;   -- Bookmark this point

    INSERT INTO order_items (...) VALUES (...);
    -- This fails!

    ROLLBACK TO after_order; -- Undo back to savepoint (order still exists)

    -- Try again with corrected data
    INSERT INTO order_items (...) VALUES (...);

COMMIT;

CREATE VIEW customer_order_summary AS

CTEs — Common Table Expressions

CTEs (introduced with the WITH keyword) are like temporary named queries. They make complex queries readable and maintainable.

WITH (CTE)
-- Find customers whose total spend is above average
WITH customer_spend AS (
    -- Step 1: Calculate total spend per customer
    SELECT
        c.customer_id,
        c.first_name || ' ' || c.last_name AS name,
        SUM(o.total_amount) AS total_spent
    FROM customers c
    JOIN orders o ON c.customer_id = o.customer_id
    GROUP BY c.customer_id, c.first_name, c.last_name
),
avg_spend AS (
    -- Step 2: Calculate the average
    SELECT AVG(total_spent) AS avg_val FROM customer_spend
)
-- Step 3: Find customers above average
SELECT cs.name, cs.total_spent, a.avg_val
FROM customer_spend cs, avg_spend a
WHERE cs.total_spent > a.avg_val
ORDER BY cs.total_spent DESC;

Recursive CTEs — Hierarchical Data

Recursive CTE (org chart)
-- Employee hierarchy (manager → reports)
WITH RECURSIVE org_chart AS (
    -- Base case: top-level employees (no manager)
    SELECT employee_id, name, manager_id, 0 AS level
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive case: find direct reports
    SELECT e.employee_id, e.name, e.manager_id, oc.level + 1
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.employee_id
)
SELECT
    REPEAT('  ', level) || name AS hierarchy,
    level
FROM org_chart
ORDER BY level, name;

Window Functions — Analytics Power

📖 30 min📊 Analytics

Window functions perform calculations across a set of rows related to the current row — without collapsing them like GROUP BY does. This is one of PostgreSQL's most powerful features.

ROW_NUMBER, RANK, DENSE_RANK

Ranking functions
SELECT
    name,
    category,
    price,
    ROW_NUMBER() OVER (PARTITION BY category ORDER BY price DESC) AS row_num,
    RANK()       OVER (PARTITION BY category ORDER BY price DESC) AS rank,
    DENSE_RANK() OVER (PARTITION BY category ORDER BY price DESC) AS dense_rank
FROM products
ORDER BY category, price DESC;

-- Get the #1 most expensive product in each category
WITH ranked AS (
    SELECT *, RANK() OVER (PARTITION BY category ORDER BY price DESC) AS rnk
    FROM products
)
SELECT * FROM ranked WHERE rnk = 1;

Running Totals and Moving Averages

Cumulative calculations
SELECT
    order_date::date            AS date,
    total_amount,
    -- Running total (cumulative sum)
    SUM(total_amount) OVER (
        ORDER BY order_date
    )                           AS running_total,
    -- 7-day moving average
    AVG(total_amount) OVER (
        ORDER BY order_date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    )::NUMERIC(10,2)            AS moving_avg_7d
FROM orders
ORDER BY order_date;

LAG / LEAD — Compare with Adjacent Rows

LAG & LEAD
-- Month-over-month revenue change
WITH monthly AS (
    SELECT
        DATE_TRUNC('month', order_date) AS month,
        SUM(total_amount) AS revenue
    FROM orders
    GROUP BY 1
)
SELECT
    month,
    revenue,
    LAG(revenue) OVER (ORDER BY month) AS prev_month_revenue,
    revenue - LAG(revenue) OVER (ORDER BY month) AS change,
    ROUND(
        (revenue - LAG(revenue) OVER (ORDER BY month))
        / NULLIF(LAG(revenue) OVER (ORDER BY month), 0) * 100,
        1
    ) AS pct_change
FROM monthly
ORDER BY month;

-- Procedure: place an order with transaction handling
CREATE OR REPLACE PROCEDURE place_order(
    p_customer_id  INTEGER,
    p_product_id   INTEGER,
    p_quantity     INTEGER
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_price      NUMERIC;
    v_order_id   INTEGER;
    v_total      NUMERIC;
BEGIN
    -- Get product price
    SELECT price INTO v_price
    FROM products WHERE product_id = p_product_id;

    v_total := v_price * p_quantity;

    -- Create the order
    INSERT INTO orders (customer_id, total_amount, status)
    VALUES (p_customer_id, v_total, 'pending')
    RETURNING order_id INTO v_order_id;

    -- Add order item
    INSERT INTO order_items (order_id, product_id, quantity, unit_price)
    VALUES (v_order_id, p_product_id, p_quantity, v_price);

    -- Reduce stock
    UPDATE products
    SET stock_qty = stock_qty - p_quantity
    WHERE product_id = p_product_id;

    RAISE NOTICE 'Order % created. Total: %', v_order_id, v_total;
END;
$$;

Logical Replication — Concepts & Overview

📖 20 min🔄 High Level

Logical replication streams row-level changes (INSERT, UPDATE, DELETE) from one PostgreSQL database to one or more others in near real-time. Unlike physical replication which copies raw disk blocks, logical replication understands the data — so you can replicate just specific tables, filter rows, or send data to a completely different PostgreSQL version. This module gives you the mental model and vocabulary. The full setup guide is in the separate PostgreSQL Logical Replication Guide document.

Why Logical Replication Exists — The Four Use Cases

Use CaseWhat You DoWhy Logical Replication Fits
Analytics offloadReplicate production tables to a separate analytics DBRun heavy reports without touching the production server
Zero-downtime migrationReplicate old DB → new DB, switch app when in syncOld and new run in parallel; cutover takes <30 seconds
Disaster recoveryKeep a warm standby always currentFailover with seconds of data loss instead of hours
Selective syncSend only certain tables or filtered rows to a subscriberPhysical replication copies everything; logical is surgical

How It Works — The Flow in Plain English

Every change you make to a PostgreSQL table is first written to the WAL (Write-Ahead Log) — PostgreSQL's internal change log. Logical replication reads that WAL, decodes it from raw binary into readable row changes, filters it to only the tables you care about, and streams those changes over the network to one or more subscriber databases, which apply them immediately.

Publication — What the Publisher Declares

A publication is a named definition on the publisher that says: "replicate these tables, for these operations." One publisher can have multiple publications serving different subscribers with different table sets.

Publication — the essentials
-- Create a publication for specific tables
CREATE PUBLICATION pub_analytics
    FOR TABLE orders, customers
    WITH (publish = 'insert, update, delete, truncate');

-- Add a table later
ALTER PUBLICATION pub_analytics ADD TABLE products;

-- See what's published
SELECT pubname, tablename FROM pg_publication_tables;

-- PG15+: replicate only matching rows (row filtering)
CREATE PUBLICATION pub_active
    FOR TABLE orders WHERE (status != 'cancelled');

Subscription — What the Subscriber Creates

A subscription is created on the subscriber side. It connects to the publisher, specifies which publication to follow, and starts receiving changes. When first created, it copies all existing rows (initial sync), then switches to live streaming.

Subscription — the essentials
-- Create subscription (run on SUBSCRIBER)
CREATE SUBSCRIPTION sub_analytics
    CONNECTION 'host=PUBLISHER_IP port=5432 dbname=mydb
                user=replicator password=StrongPass! sslmode=require'
    PUBLICATION pub_analytics
    WITH (copy_data = true, slot_name = 'slot_analytics');

-- Check replication is live (r = live replication, d = copying data)
SELECT relid::regclass AS table_name,
    CASE srsubstate
        WHEN 'r' THEN '✓ Live'
        WHEN 'd' THEN 'Copying...'
        ELSE srsubstate
    END AS status
FROM pg_subscription_rel;

-- Pause and resume replication
ALTER SUBSCRIPTION sub_analytics DISABLE;  -- pause
ALTER SUBSCRIPTION sub_analytics ENABLE;   -- resume

The One Risk You Must Know

⚠️

Inactive replication slot = publisher disk fills up

When a subscriber goes offline, its replication slot stays on the publisher and keeps accumulating WAL (the change log) — waiting for the subscriber to reconnect and catch up. If the subscriber is down for hours or days, WAL can fill the publisher's disk and crash it. This is the single most dangerous operational risk. Always set max_slot_wal_keep_size as a safety cap, and alert on inactive slots daily.

Table Partitioning

📖 25 min⚡ Scalability

Partitioning splits a large table into smaller physical pieces (partitions) while still presenting it as one logical table. Queries only scan relevant partitions — dramatically faster on billion-row tables.

When to Partition

💡

Rule of Thumb

Consider partitioning when a table exceeds ~50–100 million rows, queries almost always filter on one column (date, region, status), or you regularly archive/drop old data. Below that threshold, a good index is simpler and faster.

Range Partitioning — by Date

Most common pattern — partition orders, logs, or events by month or year.

Range partitioning by month
-- 1. Create the partitioned parent table
CREATE TABLE orders_partitioned (
    order_id      BIGSERIAL,
    customer_id   INTEGER       NOT NULL,
    order_date    TIMESTAMPTZ   NOT NULL,
    total_amount  NUMERIC(12,2),
    status        VARCHAR(50)
) PARTITION BY RANGE (order_date);

-- 2. Create individual partitions
CREATE TABLE orders_2024_q1 PARTITION OF orders_partitioned
    FOR VALUES FROM ('2024-01-01') TO ('2024-04-01');

CREATE TABLE orders_2024_q2 PARTITION OF orders_partitioned
    FOR VALUES FROM ('2024-04-01') TO ('2024-07-01');

CREATE TABLE orders_2024_q3 PARTITION OF orders_partitioned
    FOR VALUES FROM ('2024-07-01') TO ('2024-10-01');

CREATE TABLE orders_2024_q4 PARTITION OF orders_partitioned
    FOR VALUES FROM ('2024-10-01') TO ('2025-01-01');

-- 3. Add indexes ON EACH PARTITION (or the parent)
CREATE INDEX ON orders_partitioned (customer_id, order_date);

-- 4. Query as normal — PostgreSQL auto-routes to correct partition
SELECT * FROM orders_partitioned
WHERE order_date >= '2024-06-01' AND order_date < '2024-07-01';
-- Only scans orders_2024_q2 — ignores all other partitions ✅

Row-Level Security (RLS)

📖 20 min🔒 Security

Row-Level Security lets you control which rows a user can see or modify — enforced at the database level, not the application level. Perfect for multi-tenant apps where each user should only see their own data.

Why RLS Matters

🏢

Multi-tenant SaaS

Tenant A can never accidentally see Tenant B's data — even with a buggy query.

🛡️

Defense in Depth

Even if app code has a bug, the DB enforces access rules independently.

✅

Compliance

GDPR, HIPAA, and SOC2 auditors love database-level access controls.

Enable RLS and Create Policies

Basic RLS setup
-- 1. Enable RLS on the table
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- 2. Create a policy: users can only see their OWN orders
CREATE POLICY orders_isolation ON orders
    USING (customer_id = current_setting('app.current_user_id')::INTEGER);

-- 3. In your application, set the context before querying:
SET app.current_user_id = '42';
SELECT * FROM orders;  -- automatically filtered to customer_id = 42

Multi-tenant App — Full Example

Multi-tenant RLS
-- Add tenant_id to every table
ALTER TABLE customers ADD COLUMN tenant_id INTEGER;
ALTER TABLE orders     ADD COLUMN tenant_id INTEGER;

-- Enable RLS
ALTER TABLE customers ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders     ENABLE ROW LEVEL SECURITY;

-- Separate SELECT and INSERT/UPDATE policies
CREATE POLICY tenant_isolation_customers ON customers
    USING (tenant_id = current_setting('app.tenant_id')::INTEGER)
    WITH CHECK (tenant_id = current_setting('app.tenant_id')::INTEGER);
-- USING  = filter on SELECT/UPDATE/DELETE
-- WITH CHECK = validate on INSERT/UPDATE

-- Superusers bypass RLS by default. Force RLS even for table owner:
ALTER TABLE customers FORCE ROW LEVEL SECURITY;

-- Create a DB role for your app (never use superuser in app code!)
CREATE ROLE app_user LOGIN PASSWORD 'AppPass123!';
GRANT SELECT, INSERT, UPDATE, DELETE ON customers, orders TO app_user;

Node.js / Python Integration

Node.js — set tenant context before query
// In your API handler (Node.js with pg library)
async function getOrders(tenantId, userId) {
  const client = await pool.connect();
  try {
    // Set RLS context for this transaction
    await client.query(`SET LOCAL app.tenant_id = $1`, [tenantId]);
    await client.query(`SET LOCAL app.current_user_id = $1`, [userId]);

    // This query is automatically filtered by RLS
    const result = await client.query(`SELECT * FROM orders`);
    return result.rows;  // only this tenant's orders
  } finally {
    client.release();
  }
}
⚠️

Critical: Use SET LOCAL not SET

SET LOCAL scopes the setting to the current transaction only. SET persists for the entire session. In connection pools, sessions are reused — always use SET LOCAL inside a transaction to avoid tenant data leakage between requests.

pgvector — AI & Vector Embeddings

📖 30 min🤖 AI/ML

pgvector turns PostgreSQL into a vector database. This is the foundation of modern AI apps — semantic search, RAG (Retrieval-Augmented Generation), recommendations, and similarity matching. No need for a separate Pinecone or Weaviate!

What Are Embeddings?

🧠

The Core Idea

An embedding is a list of numbers (e.g. 1536 floats) that represents the meaning of text, image, or audio. Similar content produces similar vectors. pgvector stores these vectors and finds the nearest ones — "find me the 5 most semantically similar documents to this query."

Setup

    id          BIGSERIAL    PRIMARY KEY,
    title       TEXT         NOT NULL,
    content     TEXT         NOT NULL,
    embedding   vector(1536),   -- 1536 dims = OpenAI text-embedding-3-small
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- Insert a document with its embedding

VALUES (
    'PostgreSQL Indexing Guide',
    'B-tree indexes are best for range queries...',
    '[0.023, -0.011, 0.085, ...]'::vector  -- from your embedding API
);

Vector Similarity Search

Similarity operators
-- pgvector distance operators:
-- <->  Euclidean distance (L2)
-- <#>  Negative inner product
-- <=>  Cosine distance  ← best for text embeddings

-- Find top 5 most similar documents to a query embedding
SELECT
    id,
    title,
    LEFT(content, 100) AS preview,
    1 - (embedding <=> '[0.021, -0.009, ...]'::vector) AS similarity_score
FROM documents
ORDER BY embedding <=> '[0.021, -0.009, ...]'::vector  -- ASC = most similar first
LIMIT 5;

Vector Index for Speed

HNSW and IVFFlat indexes
-- HNSW index — best accuracy + speed (recommended for most cases)
CREATE INDEX idx_documents_hnsw
    ON documents USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- IVFFlat index — better for huge datasets (millions of vectors)
CREATE INDEX idx_documents_ivf
    ON documents USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);   -- lists ≈ sqrt(row_count)

-- Set search accuracy (higher = more accurate, slower)
SET hnsw.ef_search = 100;

Real-World RAG Pattern (Python + OpenAI)

Python — RAG with pgvector

Hybrid Search — Vector + Keyword

Combine semantic + keyword search
-- RRF (Reciprocal Rank Fusion) — combine vector and full-text scores WITH vector_results AS ( SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> '[...]'::vector) AS rank FROM documents LIMIT 20 ), text_results AS ( SELECT id, ROW_NUMBER() OVER ( ORDER BY ts_rank(search_vector, plainto_tsquery('index performance')) DESC ) AS rank FROM documents WHERE search_vector @@ plainto_tsquery('index performance') LIMIT 20 ) SELECT d.title, COALESCE(1.0/(60+vr.rank), 0) + COALESCE(1.0/(60+tr.rank), 0) AS rrf_score FROM documents d LEFT JOIN vector_results vr ON d.id = vr.id LEFT JOIN text_results tr ON d.id = tr.id WHERE vr.id IS NOT NULL OR tr.id IS NOT NULL ORDER BY rrf_score DESC LIMIT 10;

Key Spatial Queries

Distance, radius, nearest neighbour
-- Distance between two cities (in metres)
SELECT
    ST_Distance(
        ST_Transform(a.location, 3857),
        ST_Transform(b.location, 3857)
    ) / 1000 AS distance_km
FROM stores a, stores b
WHERE a.name = 'Hyderabad Central'
  AND b.name = 'Bangalore Tech';

-- Find all stores within 500km of a user (lon, lat)
SELECT name, city,
    ST_Distance(
        ST_Transform(location, 3857),
        ST_Transform(ST_SetSRID(ST_MakePoint(78.48, 17.38), 4326), 3857)
    ) / 1000 AS km
FROM stores
WHERE ST_DWithin(
    ST_Transform(location, 3857),
    ST_Transform(ST_SetSRID(ST_MakePoint(78.48, 17.38), 4326), 3857),
    500000   -- 500km in metres
)
ORDER BY km;

-- Nearest 3 stores (uses spatial index automatically)
SELECT name, city
FROM stores
ORDER BY location <->
    ST_SetSRID(ST_MakePoint(78.48, 17.38), 4326)
LIMIT 3;

Connection Pooling with PgBouncer

📖 20 min⚡ Scalability

PostgreSQL creates a new OS process for every connection. At 500+ connections this eats RAM and CPU. PgBouncer sits in front of PostgreSQL and reuses a small pool of real connections for thousands of app connections.

The Problem PgBouncer Solves

⚠️

Without Pooling

A Node.js app with 10 instances × 20 connections each = 200 PostgreSQL processes. Scale to 50 instances and you have 1000 processes consuming ~1GB RAM just for connection overhead. PostgreSQL starts rejecting connections. Your app crashes.

PgBouncer Pooling Modes

ModeConnection reuseSupportsBest For
Transaction ⭐After each transactionMost appsRecommended for most web apps
SessionAfter session disconnectEverythingApps using session-level features (temp tables, SET)
StatementAfter each statementSimple queriesRead-only, simple workloads only
⚠️

Transaction mode limitations

In transaction mode, SET LOCAL, prepared statements, and advisory locks don't work across transactions because connections are swapped. Use session mode if your app relies on these — or configure your ORM accordingly (Prisma, Sequelize have pgbouncer modes).

PgBouncer Configuration

pgbouncer.ini
[databases]

ecommerce = host=127.0.0.1 port=5432 dbname=ecommerce

[pgbouncer]
listen_port = 6432          ; app connects to 6432, not 5432
listen_addr = 127.0.0.1
auth_type   = md5
auth_file   = /etc/pgbouncer/userlist.txt

pool_mode        = transaction   ; recommended
max_client_conn  = 1000          ; max app connections to PgBouncer
default_pool_size = 25           ; real connections per database/user
min_pool_size     = 5
reserve_pool_size = 5
server_idle_timeout = 600

; Logging
log_connections = 0
log_disconnections = 0

Query Optimization — Deep Dive

📖 35 min⚡ Expert Level

When a query is slow, you need a systematic process to find and fix the bottleneck. This module gives you that exact playbook.

Step 1 — Read EXPLAIN Output

EXPLAIN ANALYZE BUFFERS
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT
    c.first_name, c.last_name,
    COUNT(o.order_id) AS order_count
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_date >= '2025-01-01'
GROUP BY c.customer_id
HAVING COUNT(o.order_id) > 5;

-- Key things to look for:
-- ✅ "Index Scan"      → good, using index
-- ⚠️ "Seq Scan"       → full table scan, may need index
-- ⚠️ "Hash Join"      → usually fine but watch for large hash tables
-- ❌ "Nested Loop"    → on large tables = slow (O(n²))
-- ❌ rows=1 actual=50000 → bad statistics, run ANALYZE
-- ✅ "Buffers: shared hit=200" → data from cache (fast)
-- ❌ "Buffers: shared read=200" → data from disk (slow)

Step 2 — Fix Bad Estimates with ANALYZE

Statistics maintenance
-- Update statistics for the planner (run after bulk loads)
ANALYZE customers;
ANALYZE;  -- all tables

-- VACUUM removes dead rows and updates visibility map
VACUUM ANALYZE orders;

-- VACUUM FULL reclaims disk space (locks table — use with care)
VACUUM FULL orders;

-- Check table bloat (dead tuples)
SELECT relname, n_live_tup, n_dead_tup,
    ROUND(n_dead_tup * 100.0 / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS dead_pct
FROM pg_stat_user_tables
WHERE n_dead_tup > 1000
ORDER BY n_dead_tup DESC;

Step 3 — Common Query Rewrites

Slow → Fast rewrites
-- ❌ SLOW: correlated subquery runs once per row
SELECT c.*, (
    SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.customer_id
) AS order_count
FROM customers c;

-- ✅ FAST: single aggregation + join
SELECT c.*, COALESCE(oc.order_count, 0) AS order_count
FROM customers c
LEFT JOIN (
    SELECT customer_id, COUNT(*) AS order_count
    FROM orders GROUP BY customer_id
) oc ON c.customer_id = oc.customer_id;

-- ❌ SLOW: OR prevents index use
SELECT * FROM customers
WHERE city = 'Hyderabad' OR city = 'Mumbai' OR city = 'Bangalore';

-- ✅ FAST: IN list uses index
SELECT * FROM customers
WHERE city = ANY(ARRAY['Hyderabad', 'Mumbai', 'Bangalore']);

-- ❌ SLOW: COUNT(*) on large table = full scan
SELECT COUNT(*) FROM orders;

-- ✅ FAST: estimated count (good enough for dashboards)
SELECT reltuples::BIGINT AS approx_count
FROM pg_class WHERE relname = 'orders';

Step 4 — Index Strategies

Advanced index patterns
-- Covering index: include extra columns to avoid table lookup
CREATE INDEX idx_orders_covering
    ON orders (customer_id, order_date)
    INCLUDE (total_amount, status);
-- Query only hits the index — no table access needed:
-- SELECT total_amount, status FROM orders WHERE customer_id=1

-- Expression index: index on computed value
CREATE INDEX idx_customers_email_lower
    ON customers (LOWER(email));
-- Now this uses the index:
SELECT * FROM customers WHERE LOWER(email) = 'priya@example.com';

-- Partial index: only index rows that are queried often
CREATE INDEX idx_orders_pending
    ON orders (customer_id, order_date)
    WHERE status = 'pending';
-- Much smaller index — only pending orders (maybe 1% of rows)

Key configuration parameters
-- Check current config
SELECT name, setting, unit, context
FROM pg_settings
WHERE name IN (
    'shared_buffers',         -- RAM for data cache (set to 25% of total RAM)

The Optimization Checklist

✅

Systematic Approach — In Order

1. Run EXPLAIN (ANALYZE, BUFFERS) — read the actual plan
2. Look for Seq Scans on large tables → add index
3. Check row estimates vs actuals → run ANALYZE if way off
4. Look for correlated subqueries → rewrite as JOIN
5. Check for function calls on indexed columns → use expression indexes
6. Check for missing covering columns → add INCLUDE columns
7. Check pg_stat_statements for top time-consumers
8. For complex reports: use materialized views, pre-aggregate with cron
